# SIMO OS — User Roles & Permissions

**Status (Sprint 013): real login + signup work end-to-end, every user belongs to a tenant, `role` is a real constrained enum, an Owner can invite a Staff teammate, seven modules (`customers`, `projects`, `quotes`-browsing, `tenants`, `invitations`, `activity`, `notifications`) plus the dashboard require a valid token, every one of them is filtered to the caller's own tenant (ADR-029), and a customer can now get read-only access to their own data with no account at all (ADR-030).** `POST /api/v1/auth/login`, `POST /api/v1/auth/signup`, `GET /api/v1/auth/me` (`app/auth/`, Sprint 003 + Sprint 009) are backed by real accounts — no longer a single seeded owner only. Sprint 004 wired the frontend to auth for the first time (`/login`, token storage, `/api/v1/customers/*` requiring a valid token, ADR-021). Sprint 006 extended the same requirement to `/api/v1/projects/*` (ADR-022). Sprint 007 extended it to `/api/v1/quotes/*` (ADR-023) — but **only browsing**. Sprint 008 added `/api/v1/tenants/*`, reusing the same gate. Sprint 009 (ADR-026) made "which tenant" a real, enforced fact about every user. Sprint 010 (ADR-027) formalized `role` as `UserRole` and added `require_role()`, a permission-checking dependency, attached to no route. Sprint 011 (ADR-028) added `app/invitations/` — the first module that lets a tenant have more than one user, and the first place `require_role(UserRole.OWNER)` is actually attached to a route. An Owner can now create/list/revoke a Staff invitation; the invitee accepts it (no auth required — that's the point) and becomes a real `UserRole.STAFF` user in the same tenant. Sprint 012 (ADR-029) enforced tenant isolation — every business-data route now filters by the caller's own tenant, closing the gap every sprint since 008 flagged as deferred. **Sprint 013 (ADR-030) adds `app/portal/` — a read-only client portal**, reusing the invitation token mechanism but reusable (not single-use): any authenticated tenant user can generate a link a customer opens repeatedly to see their own projects/quotes, with no `users` row and no login. This document describes the current state honestly, and the planned model for what's still ahead.

---

## 1. Current state

The frontend has a real signup + login flow. `apps/web/app/signup/page.tsx` (Sprint 009) calls `POST /api/v1/auth/signup` — company name, owner name, email, password — creating a brand-new tenant and its first (Owner) user in one call, and signs the new owner straight in. `apps/web/app/login/page.tsx` calls `POST /api/v1/auth/login`. Both store the returned JWT (`apps/web/lib/auth-storage.ts`, localStorage). `components/auth/AuthProvider.tsx` (a React context mirroring `ThemeProvider`'s shape) tracks whether a valid token is present and, since Sprint 009, also resolves and holds the signed-in user's company name (`tenantName`) — fetched via `GET /api/v1/auth/me` on mount when a stored token exists, so a page refresh doesn't lose it. `components/shell/UserProfileMenu.tsx`'s **Sign out** is real — it clears the token and redirects to `/login`. Profile and Settings remain `disabled` — nothing new to show/configure for either yet.

`/customers`, `/customers/new`, `/customers/[id]`, `/projects`, `/projects/new`, `/projects/[id]`, `/quotes`, and `/quotes/[id]` all redirect to `/login` if no valid token is present (a client-side check-on-mount guard, not Next.js middleware/SSR-level). `/quotes/new` is the one exception — it works signed out (matches `POST /quote` staying public). `lib/api.ts`'s `request()` attaches the stored token to every backend call automatically and clears it on a `401` (treating that as "session expired," not just this one call failing) — this is also what makes an old-shape (pre-Sprint-009) token self-heal: the first authenticated call after upgrading gets a `401`, the stored token is cleared, and the user is prompted to sign in again, no manual intervention needed.

`/settings` still shows a "Coming soon" state.

**No longer true as of Sprint 012 (ADR-029):** `POST /api/v1/quote` and `POST /api/v1/estimate` remain deliberately public (ADR-023), and `/api/v1/process` reads only the shared, tenant-agnostic materials catalogue — but `/api/v1/activity`, `/api/v1/notifications`, and `/api/v1/dashboard` now all require a valid token and are scoped to the caller's own tenant; they were fully public and global before this sprint. **Also resolved:** a valid token always carries a real `tenant_id` (ADR-026), and as of Sprint 012 **every protected route filters by it** — a Staff or Owner user from Tenant A can no longer list/read/create/update Tenant B's customers/projects/quotes/activity/notifications with a valid token, including via a `customer_id` supplied on a project/quote that belongs to a different tenant (rejected with `404`, not silently linked). This closes the gap this section used to describe as "the explicitly-deferred scope of Sprint 012."

## 2. Planned model (partially built)

Per the approved SaaS roadmap, Sprint 003 delivered single-tenant JWT *machinery*; Sprints 004, 006, 007, and 008 enforced "has a valid token" on the business-data/schema modules that introduced something worth protecting. **Sprint 009 made the token itself tenant-aware** (every user belongs to exactly one tenant, `NOT NULL` in the database). Sprint 010 formalized `role` as a real enum (`UserRole`, `app/auth/models.py`) and added `require_role()` (`app/auth/dependencies.py`), a reusable permission-checking dependency — machinery only, attached to no route (ADR-027). **Sprint 011 adds `app/invitations/` (ADR-028): an Owner can invite a Staff teammate by email, the invitee accepts via a one-time hashed token (no auth required to view or accept an invite — the whole point is onboarding someone with no account yet), and a real `UserRole.STAFF` user is created in the same tenant.** `require_role(UserRole.OWNER)` is now attached to `POST`/`GET`/`DELETE /api/v1/invitations*` — the first route(s) it's ever gated. Sprint 012 is where tenant isolation is actually enforced on business data.

Based on the business context this system is being built for (a stone/construction company), the anticipated roles are:

| Anticipated role | Anticipated scope | Status |
|---|---|---|
| Owner | Full access within their tenant — the role every signup's first user gets (`UserRole.OWNER`, Sprint 009, formalized as an enum Sprint 010) | **Enforced on one module** — `require_role(UserRole.OWNER)` gates all of `/api/v1/invitations*` except the public token-view/accept routes (Sprint 011, ADR-028); no other route distinguishes an Owner from a Staff user yet |
| Staff / employee | Scoped access to their assigned projects, quotes, and schedule, within their tenant | **Can now exist** — accepting an invitation (`POST /api/v1/invitations/token/{token}/accept`) creates a real `UserRole.STAFF` user (Sprint 011). Scoping what a Staff user can/can't do beyond "isn't an Owner" is still undesigned — today a Staff user can call every non-Owner-gated authenticated route exactly like an Owner can |
| Customer (client portal) | Read-only access to their own project/quote status | **Implemented, Sprint 013 (ADR-030)** — not a `users` row, exactly as anticipated: a reusable, revocable hashed token (`app/portal/`, same mechanism as invitations) grants view-only access to one customer's own projects/quotes, no account, no login. Invoice download shipped with Sprint 013 itself. Document upload/download shipped Sprint 016 (ADR-032) — staff upload a file against a customer, downloadable both by staff and via the customer's portal link. Messaging remains not implemented — still deliberately deferred. |

**The permission *primitive* is real and now enforced in one place; the permission *matrix* still isn't.** `require_role()` can enforce "one of these roles" on any route the moment there's a reason to — Sprint 011 gave it its first real reason (protecting invitation management from a Staff user). Deciding which *other* routes should eventually require `OWNER` specifically (tenant settings? billing? removing a teammate?) remains explicitly deferred — a real `UserRole.STAFF` user existing now makes that design work possible, not done. **Sprint 015 (ADR-031) resolves the "removing a teammate?" example specifically:** `app/users/` (`require_role(UserRole.OWNER)`) lets an Owner list their team and deactivate a Staff member's access. The other named examples — tenant settings, billing — remain open; this sprint answers one case, not the whole deferred question.

## 3. What to check before assuming auth is enforced

If you're reading this because you're about to build something that depends on "the current user," "the current tenant," or "permissions": `get_current_user` (`app/auth/dependencies.py`) is attached to `/api/v1/auth/me`, all of `/api/v1/customers/*`, all of `/api/v1/projects/*`, `/api/v1/quotes/*` (the browsing routes), all of `/api/v1/tenants/*`, all of `/api/v1/activity/*` and `/api/v1/notifications/*` (Sprint 012), `GET /api/v1/dashboard` (Sprint 012), and `POST`/`GET`/`DELETE /api/v1/invitations*` (via `require_role`, which wraps it). A new `get_current_user_optional` (Sprint 012, ADR-029) is attached to `POST /api/v1/quote`/`/estimate` only — those stay callable with no token at all (ADR-023), but a valid one opportunistically tags the result with the caller's tenant. `get_current_user` guarantees "a valid token, and that token's user has a real `tenant_id`" (Sprint 009) **and, as of Sprint 012, that every one of the routes listed above filters its query by that tenant** — a cross-tenant id reads as `404`, matching ADR-028's cross-tenant-lookup-leak precedent, and a `customer_id` supplied on `POST /api/v1/projects` or `POST /api/v1/quote`/`/estimate` (when authenticated) must resolve under the caller's own tenant or the request `404`s (ADR-029's relationship-bypass check). The sole deliberate exception is `materials` — a shared reference catalogue, not tenant-owned data, so no route ever filters it by tenant. `require_role(*roles)` (`app/auth/dependencies.py`, Sprint 010, ADR-027) is attached to `POST`/`GET`/`DELETE /api/v1/invitations*` as `require_role(UserRole.OWNER)` since Sprint 011 (ADR-028) — its only attachment point so far, unchanged by Sprint 012. `GET /api/v1/invitations/token/{token}` and `POST /api/v1/invitations/token/{token}/accept` are deliberately public (no `get_current_user` at all) — an invitee has no account yet when viewing/accepting an invite. `current_user.tenant_id` (the DB row, not the JWT claim — see ADR-026) is the value every tenant-scoping query now reads; `current_user.role` (a `UserRole` value since Sprint 010, and now populated with real `Staff` values since Sprint 011) is what any future `require_role(...)` call should check against. Check `docs/API_SPEC.md`'s route table's "Auth required?" column and `docs/DECISIONS.md` ADR-020/ADR-021/ADR-022/ADR-023/ADR-025/ADR-026/ADR-027/ADR-028/ADR-029 — if a route or guarantee you care about isn't listed there, nothing has changed since this document was written.
