# GeoCore — Database Schema

**Status: 8 tables as of Sprint 008/009 (the original 7 plus `tenants`); tenant-isolation-enforced as of Sprint 012.** PostgreSQL 16, SQLAlchemy 2.0 declarative models (`app/database/models.py`), Alembic migrations (`alembic/`), and a real engine/session layer (`app/database/database.py`) all exist. `users` (Sprint 003, tenant-aware since Sprint 009), `customers` (Sprint 004), `projects` (Sprint 006), `quotes` (Sprint 007), and `tenants` (Sprint 008) have real HTTP API surfaces; `materials` (Sprint 005) is real and seeded but **internal-only** — read by `/api/v1/quote`, `/api/v1/estimate`, `/api/v1/process`, not exposed as its own route (a confirmed scope decision, not an oversight).

---

## 1. What actually holds data today

### 1.1 Hardcoded catalogue (`app/data/`) — superseded by Sprint 005, `services.py` still live

- `materials.py`, `pricing.py` — the original 3-entry hardcoded dicts. **Superseded as of Sprint 005** by the database-backed catalogue (`app/materials/`, §1.4) — no longer imported anywhere, left in place per ADR-008 (archive, don't delete without approval) rather than deleted.
- `services.py` — `SERVICES: list[str]`, 4 static service names. Still live — a genuinely static company service list, not per-material data, so it wasn't part of the Sprint 005 move.

### 1.4 Material catalogue (`app/materials/`) — database-backed since Sprint 005

`MaterialService` (`app/materials/service.py`) reads the `materials` table directly (no repository interface — that pattern is for the pre-database era, per ADR-001/ADR-019; `app/materials/` follows `app/customers/`'s precedent). Seeded on startup (`app/materials/seed.py`, guarded like every other seed) with ~30 rows: 15 named materials across the 5 roadmap categories (quartz, granite, marble, porcelain, Dekton), each in 20mm and 30mm (the 30mm price is the 20mm price × a documented markup constant, not hand-picked per row). **This is an illustrative reference catalogue, not sourced from a live supplier feed** — no such data source exists in this project; see `docs/SPRINTS/sprint-005.md` for the full caveat. Consumed internally by `quotes/calculator.py`, `assistant/sales.py`, `assistant/search.py` — no `/api/v1/materials` route exists (confirmed scope decision).

### 1.2 PostgreSQL-backed repositories (`app/activity/`, `app/notifications/`) — Postgres since Sprint 002

Both are built behind a repository interface (`ActivityRepository`, `NotificationRepository` — `ABC` classes), introduced in Sprint 001 specifically so this swap wouldn't require touching the service or router layer. As of Sprint 002, `PostgresActivityRepository`/`PostgresNotificationRepository` are the default implementation — data survives a server restart, and `InMemory*Repository` still exists in the same files but is no longer constructed by default (available for tests or a future in-memory mode).

- **`ActivityEvent`** (pydantic, `app/activity/models.py`) ↔ **`activity_log`** (SQLAlchemy, `app/database/models.py`): `id`, `type`, `title`, `description`, `timestamp` — direct 1:1 mapping, `str(uuid.UUID) ↔ uuid.UUID` for the id.
- **`Notification`** (pydantic, `app/notifications/models.py`) ↔ **`notifications`** table, modelled as `NotificationRecord` in SQLAlchemy (named differently to avoid a class name collision with the pydantic model) — same direct mapping.

### 1.3 Quote persistence (`app/quotes/`) — database-backed since Sprint 007

Previously: `QuoteRequest` was calculated against and returned in the response, never saved — every quote was gone the moment the response was sent. **As of Sprint 007**, `QuoteService.create()` (`app/quotes/service.py`) wraps the existing pure `QuoteCalculator` and persists every result via `crud.create_quote(...)`, for both `POST /api/v1/quote` and `POST /api/v1/estimate` (one seam, not two copies). It also logs a real `ActivityEvent` server-side, same pattern as customers/projects.

**Important asymmetry, by schema design, not a bug:** `QuoteRequest.customer` (free-text name) is required and still works standalone — `/estimate`'s regex path has no way to resolve a real customer — but the `quotes` table has **no text name column**, only `customer_id` (FK). An unlinked quote's customer name exists only in the calculated HTTP response, never in the database row. Linking a real customer (`customer_id`, optional) is the only way a quote's customer is retrievable later, e.g. from `GET /api/v1/quotes/{id}` or its downloadable invoice.

### 1.5 Job pipeline (`app/projects/`) — database-backed since Sprint 006

`ProjectService` (`app/projects/service.py`) — same route-level pattern as `app/customers/`/`app/materials/` (ADR-019). The `projects` table gained a `status` column this sprint (migration `786f58ce4406`, safe as `NOT NULL` — the table had 0 rows). `ProjectStatus` (`app/projects/models.py`) is a 7-stage pipeline — `enquiry`, `quoted`, `booked`, `templated`, `fabricated`, `installed`, `complete` — stored as a plain `String`, same convention as `ActivityType`/`NotificationType`. `PATCH /api/v1/projects/{id}/status` is the first update endpoint in the API beyond create — a deliberate, narrow exception to the Customers precedent (list/detail/create only): a job pipeline is meaningless without a way to move a project between stages. See ADR-022.

### 1.6 Tenants (`app/tenants/`) — database-backed since Sprint 008, the 8th table

`TenantService` (`app/tenants/service.py`) — same route-level pattern as `app/customers/` (ADR-019), `Depends(get_current_user)`-gated with the existing single-tenant auth (not tenant-scoped auth — that's Sprint 009). `slug` is unique and auto-generated from `name` if not supplied (`TenantService._slugify`), with a random-suffix retry on collision. `status` defaults to `"active"` and is currently inert — nothing reads it yet (no trial/billing concept exists before Sprint 018). Creating a tenant logs a `tenant_created` `ActivityEvent`, matching every other module's `create()`. See `docs/DECISIONS.md` ADR-025 for the full reasoning, and `docs/SPRINTS/sprint-008.md` for the sprint record.

**This is the table the other 7 tables' `tenant_id` columns now genuinely point at** (see §2's Multi-tenancy note below) — but nothing yet assigns a real tenant to any row, and no query filters by one. That's Sprint 012.

**Multi-tenancy:** every one of the original 7 tables carries a `tenant_id` (UUID) column, per ADR-013 — added in Sprint 002, at zero enforcement cost, because retrofitting it onto tables with real data later would be far more expensive. **As of Sprint 008, a real `tenants` table exists and `tenant_id` on all 7 tables is a genuine `ForeignKey("tenants.id")`** (previously a bare UUID with nothing to point at) — see ADR-025. **As of Sprint 009, `users.tenant_id` is the first of the 7 to become `NOT NULL`** — every user genuinely belongs to exactly one tenant (see ADR-026) — while `customers`, `quotes`, `projects`, `materials`, `activity_log`, and `notifications` stay nullable. **As of Sprint 012 (ADR-029), every business-data query on `customers`, `projects`, `quotes`, `activity_log`, and `notifications` is filtered by the caller's `tenant_id`** — `customers.tenant_id`, `quotes.tenant_id`, `projects.tenant_id`, `activity_log.tenant_id`, and `notifications.tenant_id` each gained a plain index for it (migration `a8d91098a01e`). Columns stay nullable throughout — an anonymous `/quote`/`/estimate` call or a startup seed row still has `tenant_id = NULL`, invisible to every tenant's authenticated browsing routes. `materials` remains the sole deliberate exception: a shared reference catalogue, not tenant-owned data, so it stays unfiltered by design.

**Every change is additive or NOT-NULL-dropping.** No row is deleted or rewritten by any Sprint 036 migration, and the full pre-sprint test suite passed unchanged against the new schema. Dropping NOT NULL is a pure widening — existing rows keep every value, no existing query can start failing, and Postgres performs it as a catalogue-only change. See ADR-039 for why sentinels were rejected in favour of nullable columns, and why the universal-quoting downgrade deliberately refuses once a general quote exists.

`automations.conditions`/`actions` are the first JSON columns in this schema. The normalised alternative was rejected because both are always read and written whole, as a complete rule, and are never queried into or joined against; their shape is validated at the Pydantic boundary on every write. JSONB rather than JSON so a future "which automations use action X" query is possible without a migration.

`tasks.dedupe_key` and `automation_runs.dedupe_key` are both UNIQUE, so automation idempotency is enforced by the database rather than only attempted in code — the same defence-in-depth Sprint 024 established for `notifications.dedupe_key`.

**Legacy Safety, the migration's own hard guarantee:** the historical `ProjectStatus` strings (`enquiry`, `quoted`, `booked`, `templated`, `fabricated`, `installed`, `complete`) are never guessed, reinterpreted, or rewritten. The migration seeds an immutable `legacy_v1` template whose 7 real stage keys are, by construction, exactly those 7 values (plus its own `on_hold`/`cancelled` side stages), then binds **every project row that already existed at migration time** to `legacy_v1` at the stage matching its own `status` string, backfilled before the two new project columns are made `NOT NULL`. `projects.status` itself is not touched by this migration and remains the live field every pre-Plan-01 consumer (PipelineCounts, the pre-Task-8 frontend, a direct API integration) reads and writes exactly as before. A **new** project (created after this migration, quote handoff included) is bound to its own trade's real system template instead — never `legacy_v1`, never guessed as stone for an unknown/absent trade (`app/workflows/service.py`'s `resolve_initial_binding`, falling back to the safe `general_v1` template).

Two small, symmetric compatibility bridges keep `status` and `workflow` from ever drifting apart on a `legacy_v1`-bound project specifically (the one binding where a 1:1 stage-key mapping actually exists): the legacy `PATCH /projects/{id}/status` endpoint also moves `workflow_stage_id` to the matching stage in the same transaction, and the new `POST /projects/{id}/workflow/transition` endpoint also writes `status` when the project is legacy-bound and the target is a real (non-side) stage. A project on a real trade workflow has no such mapping, so `PATCH /status` simply leaves `workflow` untouched for it — `status` and `workflow` are two independent, equally valid views during this rollout, the same dual-field pattern `ProjectOut` itself uses.

`app/dashboard/models.py`'s `PipelineRoleCounts` and `app/automations/subjects.py`'s `project_subject` (`workflow_stage_key`/`workflow_stage_label`/`workflow_role`/`previous_workflow_role`) read the semantic `role` column above — additive alongside the unchanged `PipelineCounts`/`status`/`previous_status`, never replacing them.

**Price resolution precedence** (`app/catalogue/service.py::resolve_price_per_slab`, documented there and in ADR-044): an explicit `selling_price_per_slab` wins outright; otherwise `buy_cost_per_slab × (1 + default_markup_percent / 100)`; otherwise `buy_cost_per_slab / (1 - target_margin_percent / 100)`; otherwise `None` — never a fabricated figure. `QuoteCalculator` raises `CataloguePriceMissingError` (HTTP 400) rather than ever substituting a price, and looks up the tenant's override at the item's own `catalogue_variant_id` first, falling back to the surface-level override (`surface_variant_id IS NULL`) when no variant-specific one exists — the common case, since a tenant usually prices a surface once.

**No platform-admin role exists** (`UserRole` has only `OWNER`/`STAFF` — see docs/USER_ROLES.md), so Plan 03 deliberately does not invent one. Global (`tenant_id IS NULL`) catalogue rows are written only by the explicit, non-HTTP `python -m app.catalogue.seed` script (`app/catalogue/seed.py`) — idempotent (slug lookup before create), never wired into app startup, and never auto-publishing scraped data. A tenant's own private catalogue rows (`tenant_id` set) are written through the ordinary authenticated API by that tenant's own Owner/Staff, via `POST /api/v1/catalogue/custom-materials`.

**Deduplication is never by name alone** (`app/catalogue/dedupe.py::score_candidate_match`): a shared `material_family` is a prerequisite (mismatch scores 0 outright), a matching SKU under the same supplier/manufacturer is a near-certain match, and two surfaces that share only a name with no shared supplier/manufacturer/brand are capped well below the duplicate threshold — proven by `tests/test_catalogue.py`'s coexistence tests, so "Calacatta Gold" from two different suppliers is never silently merged.

### Sprint 043 — GeoCore Premium OS Plan 04: Job Financials + Variations

One migration, `1a2b3c4d5e6f` (parent `709c9ed313cc`), purely additive — three new tables, no existing table touched, no historical project or quote row rewritten. A pre-Plan-04 project simply has zero `project_cost_entries`/`variations` rows, exactly as if the feature had always existed and nobody had used it yet.

| Table | Columns | Notes |
| --- | --- | --- |
| `project_cost_entries` | `id`, `tenant_id` (FK, indexed), `project_id` (FK, indexed), `category` (`material`\|`labour`\|`subcontractor`\|`plant`\|`transport`\|`other`), `state` (`budgeted`\|`committed`\|`actual`), `description`, `supplier_or_payee` (nullable), `reference` (nullable), `quantity`/`unit`/`unit_cost` (all nullable — optional detail a caller may supply to *derive* `total_cost`, never used to silently recompute it), `total_cost` (NOT NULL — the one figure every aggregate sums), `cost_date`/`due_date` (nullable), `created_by_user_id` (nullable FK), `created_at`, `updated_at`. | One row is one cost item's current record. As it graduates budgeted → committed → actual, the same row is edited in place (`PATCH`), never duplicated per stage — the design decision that keeps `forecast_cost = budgeted + committed + actual` safe from double-counting without needing to reason about overlapping states across multiple rows. `category`/`state` are validated against a closed vocabulary at the Pydantic boundary, never free text. |
| `variations` | `id`, `tenant_id` (FK, indexed), `project_id` (FK, indexed), `reference` (human-readable, `V-001`/`V-002`/… — never the database id), `title`, `description` (nullable), `status` (`draft`\|`sent`\|`approved`\|`rejected`\|`void`, default `draft`), `vat_rate` (default `0.2`), `subtotal`/`vat`/`total` (all default `0`, computed by `app/quotes/general.py::price()` — the same commercial maths engine a general quote uses, not a second one), `requested_by` (nullable), `approved_at`/`approved_by_user_id` (both nullable), `created_by_user_id` (nullable FK), `created_at`, `updated_at`. `UNIQUE(project_id, reference)`. | `draft` is the only editable status; `sent` locks title/items but may still be approved/rejected/voided; `approved`/`rejected`/`void` are terminal — a correction is a new, separate variation, never a rewrite of this one (Task 24's immutability rule). `reference` numbering is sequential and independent per project. |
| `variation_items` | `id`, `variation_id` (FK, indexed), `position`, `description`, `quantity` (default `1`), `unit` (default `item`), `unit_price` (default `0`), `line_total` (default `0`), `created_at`. | Child rows of a variation, bulk-replaced (delete-then-recreate) on every draft edit rather than diffed — the same simplicity `general_v1` quote items already use. |

**Base contract value** (`app/financials/service.py::resolve_base_contract`) comes from exactly one source: the project's linked, handed-off quote (`Project.quote_id`, which `QuoteService.handoff()` only ever sets for an already-*approved* quote — see ADR-047). `Project.estimated_value` is deliberately never used here: its own docstring states it "legitimately moves as variations are agreed", making it an unsafe, mutable source for what must be a fixed, auditable base figure. A project with no linked quote has `base_contract_value = None` ("Unknown"), never a fabricated zero.

**Current contract value is always *derived***, never incremented: `base_contract_value + SUM(total) over approved variations for this project`, recomputed fresh on every read. This is what makes variation approval idempotent by construction (ADR-048) — retrying an approval can set `status = "approved"` twice, but the derived sum only ever counts each row once regardless of how many times the transition is attempted.

**Forecast cost** is the straightforward sum of a project's budgeted + committed + actual cost entries — safe from double-counting only because of the one-row-per-cost-item design above, not because of any per-state reconciliation logic. `cost_data_status` (`none`\|`partial`\|`complete`) is a completeness signal, not a data-quality one: `none` when the project has zero cost entries, `complete` only once the project's own workflow has reached its `completed` role (the one real, non-fabricated signal GeoCore has for "the job is actually finished, so its recorded costs are as complete as they will ever be"), `partial` otherwise. Every profitability figure this status gates is documented in ADR-049.

### Sprint 044 — GeoCore Premium OS Plan 05: Procurement + Materials Operations

Two migrations. `2b3c4d5e6f7a` (parent `1a2b3c4d5e6f`) is purely additive — seven new tables, plus two nullable FK columns on the existing `project_cost_entries`, no existing row rewritten. `3c4d5e6f7a8b` (parent `2b3c4d5e6f7a`) is data-only: it seeds the system `stone_v1` workflow template's `fabrication` stage with a real `materials_ready` gate (previously `NULL`), so a stone project cannot enter fabrication while a required material is still outstanding. Both are additive; a pre-Plan-05 project simply has zero procurement rows and, until this seed, no materials gate at all.

| Table | Columns | Notes |
| --- | --- | --- |
| `project_material_requirements` | `id`, `tenant_id` (FK, indexed), `project_id` (FK, indexed), `description`, `catalogue_surface_id`/`catalogue_variant_id` (nullable FK, indexed), `custom_material_name` (nullable), `material_family` (nullable), `required_quantity`/`unit` (nullable), `required_by_date` (nullable), `preferred_supplier_id` (nullable FK), `status` (`planned`\|`required`\|`ordered`\|`partially_received`\|`received`\|`allocated`\|`consumed`\|`cancelled`, default `required`), `notes` (nullable), `source_type`/`source_id` (both nullable — a polymorphic, unenforced-FK origin tag: `"quote"`, `"variation"`, or `NULL` for a manually-added requirement), `created_by_user_id` (nullable FK), `created_at`, `updated_at`. | What a project needs, independent of any purchase order — a requirement can exist before any PO is raised against it, and its `status` only ever advances forward (`app/procurement/models.py::next_requirement_status`), driven by the purchase order items linked to it. | `purchase_orders` | `id`, `tenant_id` (FK, indexed), `project_id` (nullable FK, indexed — a stock/workshop purchase has no project), `supplier_id` (nullable FK), `reference` (`PO-001`/`PO-002`/…, sequential **per tenant**, never per project — a PO's project is optional, unlike a variation's), `status` (`draft`\|`approved`\|`ordered`\|`partially_received`\|`received`\|`cancelled`, default `draft`), `order_date`/`expected_delivery_date`/`received_date` (all nullable dates), `supplier_reference` (nullable), `notes` (nullable), `vat_rate` (default `0.2`), `subtotal`/`vat`/`total` (default `0`, computed by `app/quotes/general.py::price()` — the same engine a general quote and a variation already use), `created_by_user_id`/`approved_by_user_id` (nullable FK), `approved_at` (nullable), `created_at`, `updated_at`. `UNIQUE(tenant_id, reference)`. | `draft` is the only status whose items/supplier/dates may still be edited; `approved` locks pricing and creates each item's committed cost entry; `ordered`/`partially_received`/`received` are always **derived** from receipt data (`app/procurement/models.py::derive_po_status`), never set directly; `cancelled` is reachable from any non-terminal status and reverses any committed (never actual) cost it created. |

| `project_cost_entries` | `+ purchase_order_id` (nullable FK, indexed), `+ purchase_order_item_id` (nullable FK, indexed). | Both nullable and additive — every cost entry created before this migration, and every manually-entered one after it, has both `NULL`. Set only by `ProcurementService._create_committed_costs`/`_mark_item_cost_actual`, giving procurement's own committed/actual cost entries an explicit, queryable link back to the PO that created them (`crud.list_cost_entries_by_purchase_order`), the traceability Task 17 required. |

**Financial integration, in one sentence**: approving a PO creates exactly one `committed` cost entry per item (guarded by an existence check on `purchase_order_item_id`, so retrying approval — service-layer or HTTP — never creates a second one); a full receipt flips that same row's `state` to `actual` **in place**, never inserting a second row; a partial receipt deliberately leaves the full committed amount in place until the item is completely received (the documented V1 simplification — `project_cost_entries` is one-row-per-cost-item by design, per ADR-049, and splitting a row's amount across states without a second row is not safely representable); cancelling a PO deletes its committed (never actual) cost entries outright. `tests/test_procurement.py`'s five financial-integration tests prove this holds under retry, exactly the way `tests/test_job_financials.py`'s variation-approval test already proves it for Plan 04.

**A `materials_ready` workflow gate** (`app/workflows/gates.py::MaterialsReadyGate`) blocks a stage transition only when the project has at least one requirement whose status is still in `{planned, required, ordered, partially_received}` — never when the project has zero requirements at all, so no existing stone project fixture is retroactively blocked. The system `stone_v1` template's `fabrication` stage carries this gate for real (seeded by `3c4d5e6f7a8b`); nothing else does yet.

**Lead time is advisory only, never fabricated**: `app/catalogue/models.py`'s existing `tenant_catalogue_overrides.lead_time_days` (Plan 03) is the only source a purchase order's expected delivery date may be suggested from — Plan 05 introduces no second lead-time field and computes nothing from historical delivery data.
