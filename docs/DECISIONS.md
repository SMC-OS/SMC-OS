# GeoCore — Architecture Decisions

Lightweight ADR log. Each entry: what was decided, why, and its current status. Add a new entry rather than editing history when a decision changes — note the supersession instead.

**Status categories:**
- **IMPLEMENTED** — the decision is implemented in the current codebase.
- **DECIDED-NOT-IMPLEMENTED** — a decision has been made but the implementation does not exist yet.
- **PLANNED** — explicitly planned future work/architecture that has not yet been implemented (the *what* and *when* are scheduled; the specific technical approach may still be open).
- **UNDECIDED** — no final decision has been made yet.

---

## ADR-001: Repository pattern for anything needing storage before the database exists
**Status:** IMPLEMENTED (`app/activity/repository.py`, `app/notifications/repository.py`)

Both Sprint 001 modules that need to hold data (Recent Activity, Notifications) are built as `Repository (ABC) → Service → Router`, with an `InMemory*Repository` as the only implementation today. **Why:** Sprint 002 needs to swap in PostgreSQL without rewriting the service layer, the router, or any frontend code. Any future module that needs storage before Sprint 002 lands should follow the same shape.

## ADR-002: Backend changes are additive-only until Sprint 003's restructuring
**Status:** IMPLEMENTED (Sprint 001)

New capability is added as a new module with its own `router.py`, mounted in `main.py` via `app.include_router(...)`. Existing route bodies in `main.py` are not edited unless the task is specifically about that route. **Why:** the brief for Sprint 001 required every existing endpoint to keep working exactly as before, and this was the simplest way to guarantee it — verified by smoke-testing every original route after each change.

## ADR-003: Single frontend API client
**Status:** IMPLEMENTED (`apps/web/lib/api.ts`)

No component calls `fetch()` directly — every backend call goes through `lib/api.ts`. **Why:** makes the future move to `/api/v1`, auth headers, or a WebSocket layer a one-file change instead of a search-and-replace across every component.

## ADR-004: Polling now, swappable for real-time later
**Status:** IMPLEMENTED (`apps/web/hooks/usePolling.ts`)

Every live panel (dashboard stats, activity, notifications) polls every 5 seconds through one shared hook, rather than each panel implementing its own interval. **Why:** the brief asked for the dashboard to be "prepared for WebSockets later" without implementing them yet — routing all live data through one primitive means a future real-time layer replaces one function, not every consuming component.

## ADR-005: Class-based dark mode via Tailwind v4 custom variant
**Status:** IMPLEMENTED (`apps/web/app/globals.css`, `components/theme/ThemeProvider.tsx`)

Tailwind v4 removed the `darkMode: "class"` config option; class-based toggling is instead enabled with `@custom-variant dark (&:where(.dark, .dark *));` in CSS. Theme is persisted to `localStorage` and applied via an inline `<script>` in `layout.tsx` before hydration to avoid a flash of the wrong theme. **Why:** the brief required dark mode support with a manual toggle, not just OS-preference following.

## ADR-006: Honest UI over fake functionality for unbuilt modules
**Status:** IMPLEMENTED (Sprint 001 — Customers, Projects, Settings)

Where a feature isn't built yet, the UI says so explicitly (a "Coming in Sprint N" badge) rather than a dead button or a form that silently fails. Where a form can't persist a real record yet, it still does something real — logs a genuine `ActivityEvent` — instead of pretending to save. **Why:** direct instruction from the person building this ("Do NOT use dead buttons or fake placeholders"), and it keeps the app demonstrably truthful about its own state.

## ADR-007: No new frontend dependencies without a concrete need
**Status:** IMPLEMENTED (Sprint 001)

The icon set (`components/ui/icons.tsx`), the `cn()` classname helper (`lib/utils.ts`), and dropdown/click-outside handling (`hooks/useClickOutside.ts`) are hand-rolled rather than pulling in `lucide-react`, `clsx`, or a headless UI library. **Why:** the app doesn't need them yet at this scale; revisit if/when the component surface grows enough to justify the dependency weight. Not a permanent ban — a reasoned trade-off for the current size of the app.

## ADR-008: Archive, don't delete, obsolete files
**Status:** IMPLEMENTED (`apps/web/_legacy/`)

Files identified as dead or duplicate are moved to `_legacy/` with a documented reason in `_legacy/README.md`, not `git rm`'d or deleted from disk. **Why:** explicit standing instruction — nothing gets permanently removed without separate approval.

## ADR-009: `BrainRouter` is a temporary keyword dictionary, not real AI
**Status:** IMPLEMENTED as a known placeholder, not a final design

`app/brain/router.py` maps literal keywords ("price", "quartz", "instagram"...) to an agent name via a Python `dict`. This is explicitly acknowledged as a stand-in, not a design decision to keep. Its eventual replacement is tracked separately as ADR-017 (PLANNED).

## ADR-010: ORM and migrations — SQLAlchemy 2.0 + Alembic
**Status:** IMPLEMENTED (`app/database/database.py`, `app/database/models.py`, `alembic/`)

Recommended pairing for FastAPI + PostgreSQL. Standard, well-supported, no exotic alternative considered necessary at this scale.

## ADR-011: Auth strategy — JWT bearer tokens, not server-side sessions
**Status:** IMPLEMENTED (Sprint 003 — `app/auth/`)

Stateless tokens were chosen over sessions so a future mobile app or client portal doesn't need a rework to authenticate. `POST /api/v1/auth/login` issues an `HS256` JWT (`sub`=user id, `exp`), `GET /api/v1/auth/me` validates one via `app/auth/dependencies.py`'s `get_current_user`. Passwords are `bcrypt`-hashed in the new `users.password_hash` column. See ADR-020 for the scope decision on where this is actually enforced.

## ADR-012: API versioning — `/api/v1` prefix
**Status:** IMPLEMENTED (Sprint 003)

Every route except `GET /`/`GET /health` (kept unversioned as infra/health-check endpoints) now lives under `/api/v1` (see `docs/API_SPEC.md`). Cutover was clean, not dual-mounted — the old unprefixed paths return `404` — because only the frontend consumes this API and there was no external client to break.

**Update, Sprint 018:** ADR-034 adds unversioned infrastructure route `GET /ready`; no product route moved or became unversioned.

## ADR-013: Multi-tenancy model — row-level `tenant_id`, not separate schemas
**Status:** IMPLEMENTED for the column (all 7 tables, Sprint 002); IMPLEMENTED as a real FK (Sprint 008, see ADR-025); IMPLEMENTED for enforcement (Sprint 012, see ADR-029) — `materials` is the sole, deliberate exception (shared reference catalogue, not tenant-owned data)

Simpler to operate at this scale than per-tenant schemas. Adding the column early (Sprint 002) even though it isn't enforced until Sprint 012 was judged cheap insurance against an expensive later migration. **Update, Sprint 008:** a real `tenants` table now exists and the column is a genuine `ForeignKey("tenants.id")` on all 7 tables (previously a plain nullable UUID with no table to point at) — see ADR-025 for the full detail. Still nullable, still nothing reads or filters by it today; that's Sprint 012.

## ADR-014: Frontend data fetching — hand-rolled polling now, TanStack Query later
**Status:** DECIDED-NOT-IMPLEMENTED (TanStack Query adoption planned for Sprint 004)

`usePolling` (ADR-004) is deliberately minimal. TanStack Query is the planned upgrade once more than one screen needs caching/deduping of live data — not adopted in Sprint 001 to avoid a dependency the app didn't need yet.

## ADR-015: AI provider — OpenAI SDK for router/estimator/assistants
**Status:** DECIDED-NOT-IMPLEMENTED (Sprint 006 onward)

`openai` is already in `requirements.txt` but is not imported anywhere in `app/` yet. ElevenLabs (also installed, also unused) is reserved for a future voice module, not prioritised before v1.0.

## ADR-016: Hosting / infrastructure
**Status:** UNDECIDED

Candidates noted (Render/Railway/Fly.io for backend + managed Postgres, Vercel for the Next.js frontend) but no hosting provider has been selected. This blocks nothing in Sprint 002's local development work, but needs resolving before any deployment. Not to be conflated with PLANNED — there is no committed choice here yet, only options under consideration.

## ADR-017: Real AI-based intent router, replacing `BrainRouter`'s keyword dictionary
**Status:** PLANNED (Sprint 008, per `docs/ROADMAP.md`)

The *what* and *when* are scheduled — `BrainRouter` (ADR-009) is explicitly not the long-term design, and Sprint 008 is where it gets replaced. The *how* is not yet decided: whether that's LLM-based classification, embeddings-based similarity, or another approach, and which provider, has not been chosen. Distinct from DECIDED-NOT-IMPLEMENTED entries above, where the specific technical approach is already settled.

## ADR-018: Local PostgreSQL via a single-service Docker Compose file
**Status:** IMPLEMENTED (`docker-compose.yml`)

One `postgres:16-alpine` service, no other infrastructure (no pgAdmin, no app container, no production deployment config). Credentials come from the root `.env` (gitignored; `.env.example` is the tracked template) via `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB`/`POSTGRES_PORT`, with sensible defaults if unset. **Why:** gives every developer a reproducible local database with one command (`docker compose up -d`) without deciding anything about production hosting — ADR-016 (hosting) remains UNDECIDED and this doesn't presuppose an answer to it.

## ADR-019: Postgres-backed repositories open a session per call, not via FastAPI dependency injection
**Status:** IMPLEMENTED (`app/activity/repository.py`, `app/notifications/repository.py`)

`PostgresActivityRepository`/`PostgresNotificationRepository` call `SessionLocal()` directly inside each method (`with SessionLocal() as db:`) rather than receiving a session through FastAPI's `Depends(get_db)`. **Why:** `activity_service`/`notification_service` are module-level singletons constructed once at import time (ADR-001 predates the database and this hasn't changed), not per-request objects — there is no request-scoped session available to inject into them. `app/database/database.py`'s `get_db()` dependency exists for future route-level code (Sprint 004+, once `customers`/`quotes`/`projects` get real endpoints) that isn't built around a singleton and can take a request-scoped session normally. `app/auth/` (Sprint 003) is the first module to actually use it, per ADR-011.

## ADR-020: Sprint 003 auth ships as machinery only — no existing route is gated by it
**Status:** IMPLEMENTED (Sprint 003); superseded for `customers` specifically by ADR-021 (Sprint 004)

`get_current_user` (`app/auth/dependencies.py`) is a working, reusable FastAPI dependency, but it is not attached to any of the routes in `docs/API_SPEC.md` — `/api/v1/quote`, `/api/v1/activity`, `/api/v1/notifications`, etc. all remain fully public. **Why:** deliberate scope decision made with the person building this before Sprint 003 started. There's no real per-user data yet (Sprint 004's CRM is the first module that will have any), so protecting today's routes would mean the frontend needs an `Authorization` header on every call with only one seeded user to test against, for no actual data-isolation benefit. Enforcement is deferred to whichever future sprint first has something worth protecting. This remains historically accurate for Sprint 003 — Sprint 004 is that future sprint, for `customers` only (see ADR-021); `/quote`, `/activity`, `/notifications`, etc. are still fully public.

## ADR-021: `customers` is the first module with enforced JWT auth
**Status:** IMPLEMENTED (Sprint 004 — `app/customers/router.py`)

All three `/api/v1/customers/*` routes require `Depends(get_current_user)` — this is exactly the trigger ADR-020 described: real per-user business data (customer records) now exists. **Why now, and why customers first:** Sprint 004 is literally the first sprint to introduce real business data via the roadmap; leaving it public would mean the first genuine CRM data in the system is unauthenticated while the machinery to prevent that already existed. **Consequence:** the frontend needed a way to obtain and hold a token for the first time — `apps/web/lib/auth-storage.ts` (localStorage), `components/auth/AuthProvider.tsx` (React context, mirrors `ThemeProvider`'s shape), and a new `/login` page were added as the minimum needed to support this, not a full account/settings UX. `lib/api.ts`'s `request()` now attaches the stored token to every call (harmless on the still-public routes) and clears it on a `401`. Every other route from Sprint 001–003 remains public, unaffected by this decision — enforcement was applied surgically to the one module that triggered it, not broadly.

## ADR-022: `projects` is the second module with enforced JWT auth; its status-update endpoint is the first write beyond create
**Status:** IMPLEMENTED (Sprint 006 — `app/projects/router.py`)

All four `/api/v1/projects/*` routes require `Depends(get_current_user)`, extending ADR-021's reasoning: projects are real business data linked to real customers, so the same logic applies. **No new frontend auth work was needed** — Sprint 004's login/token plumbing already covers any protected route, `lib/api.ts`'s `request()` already attaches the stored token everywhere.

**The one deliberate deviation from the Customers precedent:** Sprint 004 shipped list/detail/create only, no update. A "job pipeline" (`enquiry → quoted → booked → templated → fabricated → installed → complete`) is meaningless without a way to move a project between stages, so `PATCH /api/v1/projects/{id}/status` exists as a narrow, single-purpose exception — it can only change `status`, nothing else about a project. This is the first update-beyond-create endpoint in the API. Every other route's "no update" posture (customers, materials) is unaffected — this was a reasoned, scoped exception for the one feature that structurally required it, not a general policy change.

## ADR-023: `quotes` is the third module with enforced JWT auth — but only its browsing routes, not creation
**Status:** IMPLEMENTED (Sprint 007 — `app/quotes/router.py`)

`GET /api/v1/quotes`, `GET /api/v1/quotes/{id}`, and `GET /api/v1/quotes/{id}/invoice` require `Depends(get_current_user)` — real business data, same reasoning as ADR-021/ADR-022. **The deliberate asymmetry:** `POST /api/v1/quote` and `POST /api/v1/estimate` (where a quote is actually created) stay public. Locking those down would mean an unauthenticated visitor could no longer get a price estimate at all — a regression against the original engine's contract, and `/estimate`'s free-text path has no notion of "the current user" to check anyway. Only *browsing what's already been calculated* (the list, a specific record, its invoice) is gated. This is a genuinely different shape from customers/projects, where creation and browsing are both protected — a considered choice, not an inconsistency.

**Also this sprint:** quotes are persisted for the first time (`app/quotes/service.py` wraps the existing pure `QuoteCalculator`), and `POST /api/v1/quote/pdf` is removed in favour of `GET /api/v1/quotes/{id}/invoice` — generating an invoice now requires an already-persisted quote, downloadable again later, not just once at calculation time. See `docs/SPRINTS/sprint-007.md` for the full design (including why `quotes` has no text customer-name column, only `customer_id`).

## ADR-024: AI Quotation Generator v1 extracts structured fields only, never computes pricing
**Status:** IMPLEMENTED (AI Quotation Generator v1, `d306c99`)

`app/quotes/ai_draft.py`'s `AIDraftService` and `app/quotes/ai_models.py`'s `AIQuoteDraft` schema have no price/VAT/total field anywhere — not just an instruction the model is told to follow, but a structural guarantee: the pydantic response shape it's forced into via OpenAI's structured outputs has nowhere to put a monetary figure, so a bad or manipulated model response can extract a wrong material or a wrong length, but it cannot inject a price into the system. Every extracted value is also re-validated server-side against the real material catalogue and known thickness values (`AIDraftService._validate`) before being returned — three layers total: (1) structured-output JSON-shape enforcement, (2) refusal/error handling, (3) server-side truth-checking against the database, which is the layer that actually matters. **Why:** pricing is GeoCore's core business logic (`app/quotes/calculator.py`) — letting an LLM anywhere near it, even indirectly, would mean a hallucinated or adversarially-prompted number could reach a customer's invoice. The AI's job is narrowly "turn free text into a pre-filled form for a human to review," never "decide what something costs." (This ADR was referenced by `ai_draft.py`'s docstring before it was written — added in Sprint 008 to close that gap, not a Sprint 008 design decision itself.)

## ADR-026: Tenant-aware authentication — `users.tenant_id` becomes real, JWT gains a `tenant_id` claim
**Status:** IMPLEMENTED (Sprint 009)

Sprint 008 (ADR-025) built the `tenants` table and made every `tenant_id` column a real FK but left every one of them nullable and unenforced. Sprint 009 makes `users.tenant_id` — and only that one column — actually load-bearing: it's now `NOT NULL` (migration `c28dd4348080`), every user belongs to exactly one tenant, and `POST /api/v1/auth/signup` creates a new `Tenant` + its first `User` (role `"Owner"`) together, reusing `app.tenants.service.tenant_service.create()` rather than duplicating slug-generation logic. The other 6 tables (`customers`, `quotes`, `projects`, `materials`, `activity_log`, `notifications`) stay nullable — this sprint is deliberately narrow, not a preview of Sprint 012's full enforcement.

**JWT shape change, clean cutover:** `create_access_token()` now embeds `tenant_id` alongside `sub`; `decode_access_token()` returns the whole payload instead of just the `sub` string. `get_current_user` rejects any token missing a `tenant_id` claim — which is every token issued before this sprint — with a `401`, the same "old shape just stops working, no dual-mode shim" precedent ADR-012 set for the `/api/v1` prefix cutover. **The database row remains the actual authority**, not the claim: `get_current_user` still fetches the full `User` row by `sub` and returns it; the `tenant_id` claim is only checked for presence/shape, never substituted for `user.tenant_id`. This avoids two sources of truth ever disagreeing.

**Backfill, not a breaking migration:** the pre-Sprint-009 seeded owner account (created before `tenants` existed, `tenant_id` was `NULL`) is assigned to a newly-created "Default Workspace" tenant by the migration itself before the `NOT NULL` constraint is added — no manual intervention needed, no account left orphaned. `app/auth/seed.py` now goes through `AuthService.signup()` (the same code path a real company's first signup uses) instead of a bare `create_user()` call, so the seeded owner and every future first-user-of-a-company are created identically.

**Explicitly out of scope, by design:** teams/multiple users per tenant beyond the Owner (Sprint 010 — roles/permissions), invitations (Sprint 011), and — critically — no query in any *business-data* module (`customers`, `projects`, `quotes`, `materials`, `activity`, `notifications`, `dashboard`) was touched or gained a tenant filter. A logged-in user now definitely belongs to a tenant, but nothing yet uses that fact to isolate their data from another tenant's — that remains Sprint 012, unstarted.

## ADR-025: Multi-tenancy — a real `tenants` table, still fully unenforced
**Status:** IMPLEMENTED for the schema (Sprint 008); IMPLEMENTED for enforcement (Sprint 012, see ADR-029)

Sprint 002 added a nullable `tenant_id` UUID column to every table as cheap insurance (ADR-013), with no `tenants` table to point at and nothing reading it. Sprint 008 cashes that in: a real `tenants` table now exists (`id`, `name`, `slug` unique, `status`, `created_at`), and all 7 existing `tenant_id` columns are converted from a bare UUID into a real `ForeignKey("tenants.id")` — via two separate, independently-revertible Alembic migrations (create the table; then add the 7 FK constraints), not one bundled change. Every column stays **nullable** and **no query anywhere is filtered by it** — every existing route keeps reading/writing across all rows exactly as before Sprint 008, verified by the full existing test suite passing unchanged. A minimal `app/tenants/` module (list/get/create, `Depends(get_current_user)` — the existing single-tenant auth gate, reused rather than inventing a new one) exists so the table has something to populate it, but nothing yet ties a logged-in user to a specific tenant row. **Why split into two migrations:** the table-creation and the FK-constraint-addition are independently safe and independently revertible — if the FK step ever needed to be rolled back alone (e.g. a constraint-naming issue), the table and any rows in it wouldn't need to go with it. **Why `status` defaults to `"active"`, not `"trial"`:** no trial/billing concept exists yet (that's Sprint 018+); defaulting to a status the system doesn't yet act on differently would be a value with no behaviour behind it, and defaulting to something implying a lifecycle that doesn't exist would violate ADR-006's honesty precedent. **What this is not:** tenant-aware authentication (Sprint 009 — JWTs don't carry `tenant_id` yet, `users.tenant_id` isn't enforced `NOT NULL` yet) or isolation enforcement (Sprint 012 — no service method filters by tenant yet). This sprint is schema and CRUD plumbing only, the same "ship the machinery, enforce it later" shape Sprint 003's JWT auth had until Sprint 004 (ADR-020/021).

## ADR-027: Roles formalized as `UserRole`; `require_role()` added, wired into nothing
**Status:** IMPLEMENTED for the machinery (Sprint 010); DECIDED-NOT-IMPLEMENTED for enforcement (no target sprint yet — depends on Sprint 011)

`role` (`users.role`) was a free `str | None` since Sprint 003. Sprint 010 constrains it to `app.auth.models.UserRole` (`OWNER = "Owner"`, `STAFF = "Staff"`) — validated at the Pydantic/API boundary the same way `ProjectStatus` constrains `Project.status` (ADR-022's precedent): no native Postgres enum, no DB `CHECK` constraint, still a plain `String` column. `AuthService.signup()` now assigns `UserRole.OWNER.value` instead of the string literal `"Owner"`.

**`require_role(*allowed_roles)`** (`app/auth/dependencies.py`) is a dependency factory mirroring `get_current_user`'s shape: given one or more `UserRole` values, it returns a FastAPI dependency that 403s any authenticated user whose role isn't in the allowed set. **It is not attached to any route.** Every user in the system today — the seeded owner and every signup's first user — is a `UserRole.OWNER`; there is no way yet to create a `UserRole.STAFF` user (Sprint 011's invitations don't exist yet), so gating any current route by role would restrict nobody. Attaching it now would be enforcement theatre — a check that always passes isn't meaningfully enforcement, and a route wrongly gated to `OWNER`-only today would silently continue working for every real user while looking more restrictive than it is. Tested directly as a unit (`tests/test_permissions.py`), not through an HTTP route, since there is no route to test it through yet.

**Why build this now, before Sprint 011:** the roadmap explicitly separates "roles/permissions" (Sprint 010) from "invitations" (Sprint 011) — see `docs/USER_ROLES.md` §2. This sprint delivers the former in isolation: the enum and the checking primitive exist and are tested, so Sprint 011 (or whichever sprint first has a second real role to protect against) can attach `require_role(...)` to a route as a one-line change instead of inventing the mechanism at the same time it's first needed — the same "ship the machinery, enforce it later" shape ADR-011 (JWT auth) and ADR-025 (tenant FK) both already followed successfully.

## ADR-028: Staff invitations — opaque hashed token, Staff-only, `require_role(OWNER)` finally attached to a route
**Status:** IMPLEMENTED (Sprint 011)

The first sprint that lets a tenant have more than one user. `app/invitations/` (`models.py`/`service.py`/`router.py`) adds a `POST /api/v1/invitations` (Owner-only, creates a pending invite for an email), `GET /api/v1/invitations` (Owner-only, lists the tenant's invites), `DELETE /api/v1/invitations/{id}` (Owner-only, revokes one), a public `GET /api/v1/invitations/token/{token}` (lets an unauthenticated invitee see what they're accepting before committing), and a public `POST /api/v1/invitations/token/{token}/accept` (creates the `Staff` user and logs them in). This is also the first route anywhere gated by `require_role(UserRole.OWNER)` (ADR-027) — the machinery built in Sprint 010 finally has a real second role (`Staff`) to protect against, so gating `POST`/`GET`/`DELETE /invitations` by `OWNER` is meaningfully restrictive rather than enforcement theatre.

**Why an opaque hashed token, not a self-contained JWT:** a JWT would need no DB row at all, but the Owner needs to list pending invitations and revoke one before it's accepted — both require a queryable row that outlives the token's issuance. The token itself is `secrets.token_urlsafe(32)`, hashed with SHA-256 before it's ever written to the `invitations` table (`token_hash`, unique) — the same "never persist the recoverable secret" convention `password_hash` already established. The raw token exists only in `create_invitation()`'s return value and the one HTTP response that creates it; nothing else in the system, including this table, can recover it. `GET .../token/{token}` and `POST .../token/{token}/accept` re-hash the presented token and look up by `token_hash`, never by a stored plaintext value.

**Why Staff-only, not a `role` field on `InvitationCreate`:** `create_invitation()` always writes `UserRole.STAFF.value`. The `role` column exists on the table (so a future sprint can widen this without a migration), but letting an Owner mint a second Owner via this flow is a materially bigger decision — implicitly delegating full tenant control — than "invite a teammate" implies, and wasn't part of what was scoped or agreed for this sprint. Left to a future sprint if the business need actually arises.

**Why `expires_at` is a real column but `"expired"` isn't a stored status:** `status` is one of `"pending" | "accepted" | "revoked"` (plain `String`, same convention as `User.role`/`Project.status`) — `"expired"` is derived at read time (`InvitationService.derive_status()`) by comparing a still-`"pending"` row's `expires_at` against the current time, and surfaced wherever a row's status is shown (`GET /invitations`, `GET /invitations/token/{token}`) without ever writing anything back. `accept_invitation()` does the equivalent check inline (it needs to distinguish `"expired"` from `"revoked"`/`"accepted"` for its error message, and checks `status != "pending"` first so an already-revoked-then-expired row still reports `"revoked"`, not `"expired"`). Storing `"expired"` would mean either a background job to flip it (nothing like that exists anywhere in this codebase) or a stale value between expiry and the next write — deriving it is strictly simpler and can't go stale.

**Why cross-tenant invitation lookups 404, not 403:** `revoke_invitation()` treats "invitation belongs to a different tenant" identically to "invitation doesn't exist" (`InvitationNotFoundError` either way) — the same reasoning `docs/USER_ROLES.md` §3 and the tenant-scoped modules already apply: confirming *that* another tenant's invitation exists, even while correctly refusing to act on it, is itself a cross-tenant information leak.

**What this is not:** tenant data isolation enforcement in general (Sprint 012, still unstarted — this sprint's own queries are scoped by `tenant_id` because invitations are inherently tenant-scoped data, not because of a general enforcement mechanism); a permission matrix beyond "Owner can manage invitations, anyone can accept one with a valid token" (deciding which *other* routes should become `OWNER`-only remains explicitly deferred, per ADR-027); email delivery (no email is actually sent — the raw token is returned directly in the `POST /invitations` response body, the same "ship the mechanism, wire up delivery separately" shape as `docs/SPRINTS/sprint-007.md`'s invoice PDF landing before any email-sending existed); and any frontend UI (no page renders an invite-management screen or an accept-invite flow — same posture as Sprint 008's and Sprint 010's backend-only sprints, since a second role existing in the API is a precondition for a useful invite UI, not the other way around).

## ADR-029: Tenant data isolation enforcement — every business-data query filtered, cross-tenant relationship linkage rejected
**Status:** IMPLEMENTED (Sprint 012)

The gap every ADR since Sprint 008 flagged as deferred: a valid token always carried a real `tenant_id` (ADR-026), but no query anywhere filtered by it — any authenticated user of any tenant could read/write any other tenant's `customers`/`projects`/`quotes`/`activity_log`/`notifications` rows by guessing or enumerating ids. This sprint closes that gap for every business-data table.

**What changed, mechanically:** `app/database/crud.py`'s `customers`/`projects`/`quotes`/`activity_log`/`notifications` functions now take a required `tenant_id` (the `create_*` helpers for `quotes`/`activity_log`/`notifications` keep it optional — see below) and filter or check ownership by it — `list_*`/`count_*` add a `WHERE tenant_id = :tenant_id`, `get_*_by_id`/`update_*` add it to the lookup predicate so a cross-tenant id behaves identically to an unknown id (404, not 403 — consistent with ADR-028's cross-tenant-lookup-leak reasoning). Every router calling these now passes `current_user.tenant_id`. Two routers that had **no auth at all** before this sprint — `app/activity/router.py` and `app/notifications/router.py` (see `docs/USER_ROLES.md` §1's now-resolved "still true" list) — gained `Depends(get_current_user)` for the first time, the same trigger ADR-020/021 established: real per-tenant data now exists to protect. `GET /api/v1/dashboard` (`app/api/v1/core.py`) is likewise now auth-required and returns only the caller's tenant's counts, having previously been fully public and global.

**`app/tenants/router.py`:** `GET /tenants` and `GET /tenants/{id}` previously returned every tenant in the system (name/slug/status) to any authenticated caller — a real cross-tenant leak predating this sprint. Both now return only the caller's own tenant (`current_user.tenant_id`); a cross-tenant id 404s. `POST /tenants` was audited and left unchanged: creating a new, unlinked tenant doesn't read or expose any other tenant's data, so it isn't an isolation leak — whether that route should still be reachable at all now that `POST /api/v1/auth/signup` is the real workspace-creation path is a separate, explicitly deferred question.

**`POST /api/v1/quote` and `/estimate` stay public (ADR-023) — a new `get_current_user_optional` dependency (`app/auth/dependencies.py`) makes that compatible with tenant tagging.** Unlike `get_current_user`, a missing/invalid/expired token isn't a 401 — it's `None`, and the created `Quote`/logged `ActivityEvent` gets `tenant_id=None` (anonymous), which is invisible to every tenant's authenticated browsing routes rather than visible to whichever tenant happens to be logged in on the same browser. Called with a valid token, the quote is tagged with that caller's real tenant. This is why `create_quote`/`create_activity_log`/`create_notification` keep `tenant_id` optional while every *read* path requires it — creation can be anonymous, browsing never is.

**Relationship-linkage bypass, not just id lookups:** id-scoping alone doesn't stop a project or quote from being *created* with a `customer_id` belonging to a different tenant (a relationship-level bypass distinct from the id-lookup leaks above). `app/projects/service.py` and `app/quotes/service.py` each gained a `CustomerNotFoundError`, raised by `create()` when a supplied `customer_id` doesn't resolve under the caller's own tenant (`crud.get_customer_by_id(db, customer_id, tenant_id)` returns `None`), caught by the router as a 404 — the same "doesn't exist" response a genuinely-unknown id gets. For quotes specifically, this check only runs when `tenant_id is not None` (an authenticated caller) — an anonymous `/quote`/`/estimate` call has no tenant to validate ownership against, and the resulting quote is itself `tenant_id=None`, unreachable via any tenant's browsing routes regardless.

**`materials` is deliberately left unfiltered.** It's a shared reference catalogue (~30 seeded rows, identical for every tenant, no dedicated route — see `docs/DATABASE_SCHEMA.md` §1.4), not tenant-owned business data; every tenant's `/quote`/`/estimate`/`/process` calls need to resolve the same rows. Filtering it by tenant would require per-tenant seeding that doesn't exist and break pricing lookups for every tenant but the one the seed happened to run under. `users` and `invitations` were already correctly tenant-scoped since Sprint 009/011 and are unchanged by this sprint. `tenants` is the tenant, not owned by one.

**Schema change:** `customers.tenant_id`, `quotes.tenant_id`, `projects.tenant_id`, `activity_log.tenant_id`, and `notifications.tenant_id` each gained a plain non-unique index (migration `a8d91098a01e`, additive-only, no column/nullability change) so the new `WHERE tenant_id = :tenant_id` on every query doesn't sequential-scan. Every column stays nullable — the anonymous-quote/seed-row case still needs `NULL` to mean "belongs to no tenant."

**Test-suite fallout, not an app bug:** several existing test cleanup helpers deleted a `Tenant` row without first deleting the `ActivityLog` rows that now correctly FK-reference it under the *new* tenant's own id (previously always `None`, so no constraint was ever hit) — a `ForeignKeyViolation` in test teardown, not a production code path (nothing in the app itself deletes a tenant). Fixed by deleting the tenant's `ActivityLog` rows first in every affected fixture/cleanup (`tests/conftest.py`, `tests/test_tenants.py`, `tests/test_auth.py`, `tests/test_invitations.py`).

**What this is not:** a change to authentication itself (JWT issuance/validation, `get_current_user`'s core contract, and `require_role()` are untouched — this sprint only adds a second, purely-additive optional-auth dependency); a new persistence layer, a new auth system, or any change to `apps/web` (zero frontend files touched — every fix is backend + tests); and it does not touch `role`/`require_role()`'s permission *matrix* (still exactly ADR-027/028's scope) — this sprint is tenant isolation specifically, not the broader RBAC work.

## ADR-030: Read-only client portal — reusable hashed-token access, no `users` row
**Status:** IMPLEMENTED (Sprint 013)

`docs/ROADMAP.md`'s Sprint 013 bundles three distinct capabilities under "Client Portal": project/quote tracking, documents, and messaging. Confirmed by inspection: none of the three existed. Chosen scope, deliberately narrower than the roadmap line — **tracking only**, matching every prior sprint's one-capability-per-sprint cadence. Documents and messaging remain unstarted, their own future sprints. `docs/USER_ROLES.md` had already flagged the core question: a client portal "would likely need a different auth model entirely (not a `users` row)" — this sprint answers it.

**Token design reuses `app/invitations/`'s mechanism exactly** (ADR-028): an opaque `secrets.token_urlsafe(32)` value, hashed with SHA-256 before it's ever persisted (`token_hash`, unique) — the raw token exists only in `create_link()`'s return value and the one `201` response; nothing else can recover it. A DB-backed row is required for the same reason invitations needed one: an Owner/Staff must be able to list and revoke a link before/after it's used, which a self-contained JWT can't support.

**The one deliberate departure from the invitation precedent: a portal link is reusable, not single-use.** `PortalLink.status` is `"active" | "revoked"` only — there is no `"accepted"` state and no accept step. Every `GET /api/v1/portal-links/token/{token}` against an `"active"`, unexpired link just re-reads current data, unlimited times, until an Owner/Staff revokes it or `expires_at` passes. `"expired"` is derived at read time from `expires_at` (`PortalService.derive_status()`), same convention as `InvitationService.derive_status()` — never stored, can't go stale. `portal_link_expire_days` defaults to 90 (`app/core/config.py`), deliberately much longer than `invitation_expire_days`'s 7 — an invitation is a one-time "join now" prompt; a portal link is meant to stay usable for roughly the duration of a job.

**Token grants access to a customer, not a single project.** One `PortalLink` row (`customer_id`, required FK) surfaces *all* of that customer's projects and quotes within their tenant, not one specific job. Avoids a project-picker UI and a second link per job for a customer with multiple concurrent projects; no `project_id` column was added, since there's no stated future use for one (contrast `Invitation.role`, which ADR-028 kept for a real anticipated reason).

**Creation is deliberately not `require_role(OWNER)`-gated**, unlike inviting a teammate (ADR-028's reasoning: that's a materially bigger, tenant-control decision). Sharing a project link with a customer is routine Staff work — any authenticated user of the tenant can create, list, or revoke a portal link (`app/portal/router.py` has no router-level `dependencies=[...]`, same per-route mixing shape `app/invitations/router.py` and `app/auth/router.py` already use, since one route — `GET /token/{token}` — must stay fully public).

**Tenant isolation (ADR-029) from day one, not deferred to a later sprint.** `PortalService.create_link()` validates the given `customer_id` resolves under the caller's own tenant before creating a row — the exact `CustomerNotFoundError` relationship-linkage-bypass check ADR-029 added to `app/projects/service.py`/`app/quotes/service.py`, reused here rather than reinvented. The public `GET /token/{token}` route resolves `tenant_id`/`customer_id` from the token row itself, never from caller input, so a token minted under one tenant cannot structurally surface another tenant's data — confirmed by `tests/test_portal.py::test_portal_cross_tenant_isolation`. New `crud.list_projects_by_customer()`/`list_quotes_by_customer()` filter by both `tenant_id` and `customer_id` (defense in depth, even though a customer is already tenant-owned).

**Public response is deliberately minimal — no PII beyond what's needed to render the page.** `PortalPublicOut` returns `tenant_name`, `customer_name` (name only, never email/phone), `status`, `expires_at`, and project/quote lists with no internal cross-references (`PortalProjectOut` excludes `notes` — may hold internal staff remarks; `PortalQuoteOut` excludes `customer_id`). The portal confirms identity by possession of the link, not by echoing the customer's contact details back to them. **A revoked or expired token still returns `200`**, with `status` set accordingly and empty `projects`/`quotes` lists — same "always 200, the shape carries the state" convention `InvitationPublicOut` established, so a probing request against a dead link can't be used to distinguish "revoked" from "expired" from "never existed" by response code alone (only an *unknown* token hash — no row at all — returns `404`).

**Frontend:** one new public page (`apps/web/app/portal/[token]/page.tsx`), structurally the fetch/loading/error/status-conditional shell from `apps/web/app/invite/[token]/page.tsx` with the entire account-creation form half removed — no form, no `acceptInvite`-equivalent call, no redirect, just a rendered project/quote list. Confirmed the root layout has no pathname-based shell-bypass mechanism (`/login` and `/invite/[token]` already render inside the full `AppShell` today) — the portal page follows that same existing precedent rather than introducing new shell-bypass logic, out of scope for this sprint. One existing page changed: `apps/web/app/customers/[id]/page.tsx` gained a "Client portal" card (generate + copy-link, modeled directly on `apps/web/app/settings/page.tsx`'s invitation-creation UI) — no separate list/revoke UI ships this sprint; `GET`/`DELETE /api/v1/portal-links` exist and are tested but have no frontend consumer yet, the same "ship inert-but-tested machinery" precedent `require_role` had between Sprint 010 and Sprint 011.

**What this is not:** documents or messaging (still unstarted, deliberately out of scope — see above); any change to `users`, JWT issuance, or `get_current_user`'s contract; a redesign of `POST /api/v1/tenants`'s continued reachability (ADR-029's open question, still deferred); or a permission-matrix change (`require_role()`/`UserRole` untouched).

## ADR-031: Team management — soft-deactivation, no cascade to portal links
**Status:** IMPLEMENTED (Sprint 015)

`docs/USER_ROLES.md` names an open gap explicitly: "the permission *primitive* is real and now enforced in one place; the permission *matrix* still isn't... Deciding which *other* routes should eventually require `OWNER` specifically (tenant settings? billing? removing a teammate?) remains explicitly deferred." Sprint 015 answers "removing a teammate": a new `app/users/` module lets an Owner list their tenant's team and deactivate a Staff member's access, the second real `require_role(UserRole.OWNER)` attachment point after `app/invitations/` (Sprint 011, ADR-028).

**Soft-deactivation, not row deletion.** `users.is_active BOOLEAN NOT NULL DEFAULT true` (additive migration `dae9516f388b`) flips to `false`; the `User` row itself is never deleted. A hard delete isn't an option here: `Invitation.invited_by_user_id` and `PortalLink.created_by_user_id` are both `NOT NULL` foreign keys to `users.id`, so removing a row that ever invited a teammate or generated a portal link would violate those constraints and destroy real historical provenance. This matches the pattern `Invitation.status` and `PortalLink.status` already established — a status field on the row, not row deletion — applied here to `users` for the first time.

**Self-deactivation is blocked at the service layer (409, `CannotDeactivateSelfError`), and there is deliberately no separate "last owner" check.** `UserManagementService.deactivate_user()` rejects `user_id == acting_user_id` before it even queries the target row. A distinct "don't deactivate the tenant's only remaining Owner" guard was considered and rejected as unnecessary: `AuthService.signup()` always creates exactly one `Owner` per tenant, and `InvitationService.accept()` only ever creates `UserRole.STAFF` users — there is no code path in this codebase that produces a second Owner in a tenant today, so the state such a guard would protect against cannot occur. Building it now would be speculative handling for an unreachable case, not a real gap.

**A deactivated teammate's portal links deliberately keep working — no cascade-revoke.** `PortalLink` rows are tenant-owned data, filtered everywhere by `tenant_id` and never by `created_by_user_id` (the column is provenance, not an access-control key). The tenant retains legitimate access to a link it generated regardless of which staffer happened to create it, so deactivating that staffer has no effect on the link's `status`. Confirmed by a dedicated test (`test_deactivated_users_portal_links_still_resolve`) and by the manual smoke test against the real running app — a portal link created by a since-deactivated Staff user still resolved publicly after deactivation.

**`get_current_user` now has a second real rejection path.** Previously its only 401 was an invalid/missing/expired token; as of this sprint it also rejects a well-formed, unexpired token whose user row has `is_active = False`, with the identical generic `"Could not validate credentials"` detail — no signal distinguishing "deactivated" from "invalid," so a caller can't use the response to probe why their session died. This costs no extra query: `get_current_user` already fetches the user row via `crud.get_user_by_id()` on every request; checking `is_active` on that already-fetched row is free. Combined with the existing 60-minute JWT TTL, this is the first sprint where another user's action (an Owner deactivating them) can end a Staff user's already-issued, unexpired session mid-flight — previously only natural token expiry ever did.

**What this is not:** a reactivation feature (no endpoint, no UI — deactivate-only, matching the invitations/portal-links create-and-revoke-only precedent, no prior module in this codebase supports "undo" of a revoke); a fix for the pre-existing `EmailAlreadyRegisteredError`/`is_active` interaction (`crud.get_user_by_email` doesn't filter by `is_active`, so re-inviting a deactivated user's email still fails — flagged, not fixed); any other route becoming Owner-gated beyond this sprint's two new routes; or a reconciliation of `docs/ROADMAP.md`'s stale Sprint 015 line (still untouched).

## ADR-032: Client portal documents — local-disk storage, generated filenames, allowlist upload policy
**Status:** IMPLEMENTED (Sprint 016)

Closes the "documents" half of the client-portal gap deliberately deferred at Sprint 013's scoping decision (ADR-030) and named again in both Sprint 014's and Sprint 015's follow-up lists — the most repeatedly-flagged concrete gap in this repo's sprint history. Messaging, the other deferred half, remains out of scope. First binary-upload feature in this codebase; every prior "download" (invoices, quotes) generated a PDF server-side rather than persisting user-supplied bytes.

**Storage: local disk, not S3.** A new `settings.upload_dir` (`./uploads`, created on startup if missing, `.gitignore`d) holds every uploaded file. Accepted limitation, stated plainly rather than glossed over: this does not survive a redeploy to a different host, and does not scale past a single running instance — a deliberate scope decision for this sprint, not an oversight, revisited once real hosting is decided.

**Storage filename is always `uuid4()` plus the validated extension — never the user-supplied original filename.** `Document.original_filename` is retained purely as display/metadata and the download `Content-Disposition`'s `filename=`/`filename*=` value; it is never interpreted as a filesystem path. This closes path traversal by construction (no user input ever reaches a path-construction call), not by sanitizing a dangerous value after the fact. `Document.storage_filename` is excluded from `DocumentOut` — no route or response ever exposes the on-disk name to any client, staff or portal.

**Upload policy is an explicit allowlist, not a denylist, enforced before any bytes reach disk.** `app/documents/service.py`'s `ALLOWED_EXTENSIONS` permits `.pdf .doc .docx .xls .xlsx .txt .jpg .jpeg .png .heic .webp` only; everything else — including `.svg` and `.html`/`.htm`, deliberately excluded despite sometimes being treated as "documents" given both formats' real inline-script-execution histories — is rejected with `422`. `MAX_UPLOAD_BYTES` (20MB) is enforced against actual bytes written in chunked reads, not a trusted `Content-Length` header, so a client cannot bypass the cap by lying about size; a violation aborts the write, deletes the partial file, and returns `413`. No content-sniffing or magic-byte validation beyond the extension check — an accepted, documented gap: a renamed file could pass the extension check with different real content, but nothing in this codebase ever executes or inline-renders an uploaded file regardless of its true type (every download route forces `Content-Disposition: attachment`), so the practical exposure is limited to what the allowlist already bounds. No virus scanning, no S3/object storage, no per-tenant or per-customer storage quotas this sprint — all three explicitly deferred, not silently dropped.

**Customer-level attachment, not project-level.** `Document.customer_id` is the only relationship column beyond `tenant_id`/`uploaded_by_user_id` — same reasoning `PortalLink` already established (ADR-030): one customer's document list covers all their concurrent jobs, no project-picker UI, no unused nullable column.

**Route placement: the two public routes live in `app/portal/router.py`, not a new router.** Mirrors the existing invoice-download route (`GET /token/{token}/invoice/{quote_id}`) exactly, which already lives in `app/portal/router.py` and calls into a sibling module (`app/quotes/pdf.py`) for its content — `PortalService` gained `list_customer_documents()`/`get_customer_document()`, matching `get_customer_quote()`'s exact shape: the token must be `"active"`, and a document must belong to both the token's `tenant_id` AND `customer_id` — not tenant alone, or one portal link could pull a different customer's document within the same tenant. Every failure raises the same `PortalLinkNotFoundError`, so a caller can't distinguish "bad token" from "document not yours."

**Staff-side routes (`app/documents/router.py`) are not `require_role`-gated** — any authenticated tenant user may upload/list/download, matching the customer/project/portal-link creation precedent (routine work, not a tenant-control decision).

**What this is not:** messaging/chat (still deferred, the other half of the gap this sprint doesn't close); file versioning or editing (upload-and-download only); virus scanning, S3/object storage, or storage quotas (all explicitly deferred, see above); project-level document attachment; or any change to portal token design, auth, or tenant-isolation semantics established in ADR-029/ADR-030.

## ADR-033: Client portal messaging — customer-level plain-text thread with nullable staff attribution
**Status:** IMPLEMENTED (Sprint 017)

Sprint 017 closes the final part of the portal gap deferred in Sprint 013: staff and a customer can exchange messages through the existing reusable portal link. Messages belong to a customer rather than a project, matching `PortalLink` and `Document`; one thread therefore covers all of that customer's concurrent work without a project picker or unused relationship column.

Each `Message` stores `tenant_id`, `customer_id`, `sender_type`, nullable `sender_user_id`, `body`, and `created_at`. `sender_user_id` identifies an authenticated staff author and is always `NULL` for a customer author because portal customers have no `users` row. Public routes accept no caller-supplied customer identifier: both tenant and customer are derived exclusively from the active portal-link row. Staff create/list operations validate the customer under the authenticated user's tenant; unknown and cross-tenant customer identifiers return the same 404.

An inbound customer message creates one `CUSTOMER_MESSAGE_RECEIVED` activity event and one tenant-scoped informational notification so staff can discover it outside the open thread. A staff-authored message creates neither—staff are not notified about their own action. This is the first business-service call to `notification_service.create()` outside the notifications router; the existing singleton repository architecture means message, activity, and notification persistence use their established service boundaries rather than a new transaction abstraction.

Message bodies are plain text only and limited to 5,000 characters. Empty and whitespace-only bodies are rejected with 422 while accepted text is stored unchanged. Both frontends render `body` only through JSX text interpolation with `whitespace-pre-wrap`; no markdown or HTML interpretation is allowed. This escaping behavior is the feature's XSS boundary.

No rate limiting is introduced. This is an accepted gap for the first anonymous portal write endpoint and is explicitly deferred rather than silently implemented. Also out of scope: attachments, per-message read state, editing/deleting, staff-name resolution, WebSockets/SSE, and any portal-token redesign.

## ADR-034: Production runtime hardening — explicit environment policy and migration-first releases
**Status:** IMPLEMENTED (Sprint 018)

GeoCore now distinguishes `development`, `test`, and `production` through the explicit `APP_ENV` setting. Development remains the default and preserves convenient local database, CORS, upload-directory, and seed behavior. Production is fail-closed: the shared Pydantic `Settings` model rejects the repository JWT and seed defaults, short or blank secrets, enabled seeding, missing or unsafe CORS origins, the local development database URL, and a relative/missing upload path. `python -m app.core.runtime_check` provides the same validation as a read-only, sanitized release preflight; application import and Alembic configuration independently load the same validated settings.

**Migrations are a release job, never application startup.** The normative production order is configuration preflight, one-off `alembic upgrade head`, sole-head verification, Uvicorn container startup, `/health`, `/ready`, authenticated/storage smoke checks, then traffic promotion. This avoids concurrent application replicas racing to migrate and makes migration failure observable before the new application receives traffic. The default container command starts only `uvicorn app.main:app`; the application lifespan never runs Alembic.

**Startup is import-safe and environment-aware.** FastAPI's lifespan configures logging first, validates the upload mount, and runs the existing idempotent seeders only when `SEED_DATA_ENABLED` is true. Production requires the persistent upload directory to exist and be writable, and requires seeding to be false, so normal production startup neither creates sample/application data nor silently substitutes ephemeral storage. Local development/test may create a missing upload directory and retain seed convenience.

**Health responsibilities are deliberately split.** `GET /health` remains dependency-free liveness and preserves `{"status":"healthy"}`. `GET /ready` performs a bounded `SELECT 1` and returns a safe 200/503 database-reachability result. Readiness does not certify Alembic revision; release verification owns schema state. Both endpoints are unversioned, unauthenticated, and intentionally reveal no environment, version, tenant, database host, or error details.

**Production request observability stays inside the existing stack.** Middleware validates or generates an `X-Request-ID`, makes it available through context-local state, returns it on every response, and emits one `http_request_completed` record using a route template rather than a concrete/token-bearing path. Production logging is one JSON object per line on stdout/stderr with stable `startup_failed`, `readiness_failed`, `unhandled_exception`, and request-completion events. The allowlisted record format excludes query strings, authorization headers, bodies, raw exception messages, secret values, and database URLs. Development retains readable console logs with the same event vocabulary. This is not a full APM/metrics platform.

**The backend image is provider-neutral and non-root.** A Python 3.12 slim image includes the FastAPI and Alembic runtime, writes only through configured writable paths, exposes port 8000, and uses `/health` for container liveness. The same immutable image can be invoked by an operator as the release job or run with its Uvicorn-only default command. Hosting-provider selection remains ADR-016's unresolved decision.

**Local document storage remains an explicit production constraint.** `UPLOAD_DIR` must be an absolute persistent-volume mount that survives container replacement and application rollback. The supported topology is one backend instance, or multiple instances sharing the same supported filesystem; independent local disks are not safe. Volume ownership, coordinated backup/restore, and upload/restart/download verification are operator responsibilities documented in `docs/PRODUCTION_RUNBOOK.md`. S3/object storage, malware scanning, quotas, and storage redesign remain out of scope.

**Rollback keeps application and database actions separate.** An application rollback deploys a schema-compatible previous image without changing the database. Database downgrade is an explicit operator action only when the exact migration is known and tested to be safely reversible, incompatible writers are stopped, data implications are accepted, and a current restorable backup is verified. No automatic downgrade exists.

## ADR-035: Migration gate moves from a separate release-job step into the container's own startup command
**Status:** IMPLEMENTED (Sprint 033)

Sprint 032 deployed via `railway up --ci`, relying on Railway's `preDeployCommand` (a config-as-code "release job" step — `deploy/railway/api.railway.toml`) to run `alembic upgrade head` before the application started, per ADR-034. Investigation at the start of Sprint 033 found the service's Railway configuration correctly carried that `preDeployCommand`, but deploy logs for the actual deployment showed zero invocation of it — the database was still on the pre-Sprint-032 revision after a "successful" deploy. The evidence (both Sprint 032 deploys used `railway up --ci`, whose own help text says it "stream[s] build logs only, then exit[s]") points to the CLI returning before Railway's server-side deploy lifecycle — where `preDeployCommand` actually runs — completes, though this can't be fully confirmed from outside Railway's internals. Migrations were applied manually via `railway ssh ... alembic upgrade head` both times as a result.

**The fix does not depend on diagnosing Railway's exact internal behavior.** `app/core/migrate_gate.py` — runtime-config preflight, then `alembic upgrade head` under a Postgres advisory lock — is now invoked directly by the Dockerfile's own `CMD`, before it `exec`s into `uvicorn`. This runs on every container start, inside the same image, regardless of which Railway hook fires, which CLI flags are used, or whether a future deploy comes from the dashboard, a GitHub-connected build, or `railway up`. `deploy/railway/api.railway.toml`'s `preDeployCommand` is left in place as a harmless, idempotent redundant safety net.

**This still honors ADR-034's two actual concerns**, not just its literal mechanism. Concurrent-replica races are prevented by the advisory lock (`pg_advisory_lock`/`pg_advisory_unlock` around the upgrade, keyed to this application) — proven by a real two-thread test against local Postgres (`tests/test_migrate_gate.py`), not just asserted — rather than by the previous "one-off step, run once" assumption, which is required now that the same gate executes inside every replica's own startup. Migration failure is still observable before traffic: the Dockerfile's `CMD` only `exec`s `uvicorn` on a zero exit code, so a failing migration means the container never binds its health-check port, Railway's rollout never promotes it, and the previous revision keeps serving — surfaced in the same deploy logs an operator already watches, with no separate log stream to check. The FastAPI ASGI lifespan (`app/core/startup.py`, `app/main.py`) still never imports `alembic` or `subprocess` — that boundary from ADR-034 is unchanged and still enforced by `tests/test_runtime_startup.py`'s AST-level check; the gate is a separate process that only execs into the app after succeeding, not code the running application ever calls into.

**What changed in the Dockerfile contract:** the default `CMD` is no longer bare `uvicorn app.main:app` — it's `sh -c "python -m app.core.migrate_gate && exec uvicorn app.main:app ..."`. The "same immutable image can be invoked as the release job" property ADR-034 described is preserved (`docker run <image> python -m app.core.migrate_gate` still runs only the migration), it's just no longer the *only* way the migration runs — it now always runs as part of normal container startup too.

**What this is not:** a change to rollback/recovery semantics (still image-rollback-only, database downgrade still a separate explicit operator action per ADR-034); a move of migration logic into the FastAPI application itself; or a fix for whatever Railway does internally with `--ci` — that remains unconfirmed, and the gate is designed specifically so the answer doesn't matter.

## ADR-036: Tenant company identity is data, not code; the platform brand is never a tenant's trading identity
**Status:** IMPLEMENTED (Sprint 034, Workstream A)

Until Sprint 034, `app/quotes/pdf.py` hardcoded a single company's letterhead — "SIMO MARBLE & CONSTRUCTION LTD / Unit 4, Riverside Trade Park, London" — into every invoice the platform produced, for every tenant. Both invoice routes went through it, including the public portal route a customer downloads from. Tenant B's own invoice carried Tenant A's trading identity.

**Why Sprint 012's isolation sweep did not catch it.** That sprint audited *queries*, and every business-data read is correctly filtered by `tenant_id` — still is. This leak was never in a query. It was a literal string in a render path, a class of cross-tenant disclosure that query auditing cannot surface. ADR-029's posture is sound; its coverage was incomplete.

**The rule now enforced in one place** (`app/tenants/identity.py`): the identity on a customer-facing document is always the tenant that owns the document. Three invariants follow, and each is a real failure mode rather than a preference:

1. **Never the platform's brand.** GeoCore is the product a business subscribes to, not the business its customer is buying from. Substituting the platform name for the old hardcoded company would be the same defect wearing different clothes.
2. **Never another tenant's details, and no global default.** An unconfigured tenant falls back to its own workspace name and terminates there. A caller supplying no identity gets a document with *no* letterhead — an unattributed invoice is recoverable, one carrying the wrong company's name is not.
3. **Never a fabricated statutory number.** `company_number`/`vat_number` render only when the tenant actually supplied them. An invented company registration or VAT number on a UK invoice is a legal defect, not a formatting one, so absence omits the line rather than filling it.

**Backfill preserved historical output rather than silently changing it.** Every existing invoice already rendered the Simo letterhead, so a blank operating tenant would have changed what its customers see. Two conservative rules: a database holding exactly one tenant has that tenant backfilled (no second tenant could wrongly inherit it, and the production tenant may legitimately be named "Default Workspace"); otherwise only tenants identifiable as Simo Marble & Construction by name or slug. Only the legal name and address already being printed were backfilled. Statutory numbers were left NULL by rule 3.

## ADR-037: The platform is renamed to GeoCore; persisted keys migrate, infrastructure identifiers do not
**Status:** IMPLEMENTED (Sprint 034, Phase 2)

The platform is renamed from SIMO OS to GeoCore across user-visible surfaces: application chrome, page metadata, marketing copy, subscription plan names (`GeoCore Pro`, `GeoCore Business`), and living documentation. This separates the product brand from Simo Marble & Construction Ltd, which is one tenant of the platform (ADR-036), not the platform itself.

**Renaming a persisted key is a data migration, not a find-and-replace.** Three `localStorage` keys already exist in real browsers. `simo-os-token` holds the JWT: renaming it naively would have logged out every signed-in user the moment the rebrand deployed — an outage indistinguishable, from the outside, from a broken auth system. All three are therefore read through `readMigratedValue()` (`apps/web/lib/storage-keys.ts`), which prefers the new key, falls back to the legacy one exactly once, and carries the value forward. `clearToken()` clears both, so a sign-out cannot leave a valid JWT under the old name for the next read to resurrect. The pre-hydration theme script in `app/layout.tsx` reads both keys too, or a returning dark-mode user would flash light on their first post-deploy load. Every accessor is wrapped in try/catch: `localStorage` itself throws in Safari private mode, and a throwing storage read during module init would take the app down rather than degrade to signed-out.

**Three classes of identifier were deliberately NOT renamed**, because the rename would carry real risk and no user-visible benefit:

| Identifier | Why it stays |
|---|---|
| `UPLOAD_DIR` = `/var/lib/simo-os/uploads` | The production persistent-volume mount. Renaming it orphans every uploaded client-portal document. A path is not branding. |
| Logger name `simo_os` | Renaming silently breaks any log-based alerting or saved query keyed to it. Invisible to customers; a live operational hazard to change casually. |
| Database name `simo_os`, table and column names | Renaming a database is a migration with downtime and rollback complexity, for zero customer-visible effect. |

Recorded here so a future contributor finding `simo-os` in these three places knows it is a decision, not an oversight.

**One safety guard was widened rather than moved.** The production configuration check rejects development defaults. The seed-admin default became `owner@geocore.local`, but `owner@simo-os.local` is still rejected in production: a deployment that carried the old value through the rename must not start passing a safety check merely because a constant changed.

## ADR-038: The apex serves a separate marketing application, never the authenticated app
**Status:** IMPLEMENTED (Sprint 034, Phase 2)

`geocore.one` serves `apps/marketing`, a separate Next.js application. `app.geocore.one` serves `apps/web`. They are not the same deployment and are not routed by host within one app.

**Why not point the apex at `apps/web`.** That app's root route is the authenticated dashboard; an anonymous visitor is redirected to `/login`. Pointing the apex there would resolve the strongest URL the brand owns to a login redirect: nothing for a crawler to index, and a first impression that is a gate. A 301 from the apex to the application was considered and rejected for the same reason, with the added cost of being hard to reverse once inbound links accumulate.

**Why a separate app rather than host-based routing inside `apps/web`.** Independent deploys and independent blast radius: a marketing copy change cannot break the authenticated application, and the public site carries none of the app's client-side auth bundle. The marketing app is statically prerendered with no API dependency, so it stays up even if the API is down — which is exactly when someone is most likely to be looking at the public site.

**Indexability is asymmetric and deliberate.** `apps/marketing` is indexable only when `APP_ENV=production` *and* its canonical origin is `https://geocore.one`, so staging deploys of the same image exclude themselves rather than competing with production. `apps/web` returns `Disallow: /` unconditionally — there is no environment in which indexing the application is correct, and two concrete harms if it happens: the login page outranking the marketing site for brand queries, and token-scoped portal/invite URLs (capability tokens, not login-protected pages) being crawled and archived.

**A build-time trap, guarded by a test.** Next prerenders `robots.txt`, the robots meta tag and the canonical URL at build time, so indexability is baked into the image, not read at runtime. If `APP_ENV=production` were dropped from `apps/marketing/Dockerfile`, the production image would ship `noindex, nofollow` and `Disallow: /`: the site comes up, every page returns 200, nothing errors, and geocore.one never appears in search results. `apps/marketing/indexability.test.mjs` asserts that contract in CI precisely because the failure is otherwise invisible.

## ADR-039: A quote declares its kind; stone becomes one specialism among twelve, not the shape of the schema
**Status:** IMPLEMENTED (Sprint 036, Workstream E)

Until Sprint 036, `quotes` was not a quote table — it was a worktop table. `material`, `thickness`, `kitchen_length` and `length_mm` were all NOT NULL, so a quote could not physically be inserted without slab dimensions. `quote_items` (Sprint 033) was genuinely multi-line, but every line was a slab priced by area ÷ slab area × slab price. There was no way to express "Strip out existing bathroom — 2 days labour @ £320/day", let alone a roofing, groundworks or rewire quote.

That is not a missing feature. It is the product's central claim contradicted by its own schema: GeoCore is sold as an operating system for construction and renovation businesses, and its quote table could only describe stone.

**The fix is a discriminator, not a rewrite.** `quotes.quote_kind` is `'stone' | 'general'`; `quote_items.line_kind` is `'stone' | 'labour' | 'material' | 'other'`. Both are NOT NULL with a `'stone'` server default, which states a fact about every existing row rather than guessing one — before this migration, a quote could not have been anything else.

**NOT NULL was dropped on the eight stone-only columns rather than filling them with sentinels.** A general quote genuinely has no material, thickness or run length. Writing `'N/A'` or `0` would put a lie in the data to avoid changing the schema, and every reader downstream would then need to know which sentinel meant "absent". Dropping NOT NULL is a pure widening: every existing row keeps every value, no row is rewritten, no existing query can start failing, and Postgres performs it as a catalogue-only change.

**`quote_items.quantity` was widened INTEGER → DOUBLE PRECISION.** A stone line is 2 slabs; a labour line is 2.5 days. The JSON a client sees changes from `1` to `1.0`, which is the same number to Python's `==`, to JavaScript's `===` and to `String()` — verified against every existing assertion before the change was made.

**The two kinds share a lifecycle and share no pricing.** Draft → sent → approved → project is identical whatever trade a quote is for, so approval, handoff, the PDF and the portal are common code. Pricing is not: the stone path still runs `QuoteCalculator` against the material catalogue, and the general path is `quantity × unit_price` summed, in a module (`app/quotes/general.py`) that takes no `Session` because it needs no catalogue at all. `POST /api/v1/quote` (the public stone calculator, ADR-023) is untouched; `POST /api/v1/quotes` is the new authenticated general path.

**Rounding is stated once and shared.** Each line is rounded to 2dp, then the lines are summed. Summing unrounded floats and rounding at the end produces a total the line items on the customer's own PDF do not add up to — the one arithmetic error a quote must never make. The frontend's live preview implements the same rule deliberately, so what is on screen is what gets saved; the server re-prices from the same lines on submit and its answer is authoritative.

**The downgrade refuses rather than destroying.** Reversing this cannot silently succeed once a general quote exists: NOT NULL cannot be restored while rows legitimately hold NULL there, and deleting a tenant's real quotes to make a schema fit is destruction disguised as a migration. `downgrade()` raises, names the counts, and tells the operator what they have to decide. It reverses cleanly on a database that only ever held stone quotes, which is the only case where reversal is lossless.

**Stone was not demoted to a bug.** It is one of twelve trades in `app/trades/catalogue.py`, it keeps its own specialist quote form at `/quotes/new/stone`, and that form is offered from the general builder rather than hidden — for a worktop job it is the better tool, because it prices from the catalogue instead of by hand.

## ADR-040: Automations act only inside the workspace, and every attempt is recorded
**Status:** IMPLEMENTED (Sprint 036, Workstream G)

GeoCore has no outbound email, SMS or messaging infrastructure. That was verified across the whole repository during Sprint 036 discovery — no provider dependency, no configuration, no code path. An automation action that claimed to "email the customer a review request" would therefore be a lie in the product, and the first time a builder discovered their review requests had never been sent, they would rightly stop trusting every other automation too.

**So the action set is closed and internal**: `create_notification`, `create_task`, `draft_message` (which prepares a message and hands it to a human as a task — a task with a body, not a transmission) and `create_project_from_quote` (which delegates to the already-audited, already-idempotent `quote_service.handoff`). `GET /api/v1/automations/meta` returns `delivery.external_delivery_available: false` and the note the UI displays, so the honest statement comes from the backend and stays true the day delivery is genuinely built rather than being copy someone has to remember to change. A backend test asserts the action set against a literal list, so adding a sending action fails CI and has to be a deliberate decision.

**Three invariants, each defending a specific failure mode:**

1. **An automation can never break the thing that triggered it.** Dispatch happens after the triggering change has committed, and every run is wrapped: an exception becomes a `failed` AutomationRun row carrying the message, and is swallowed. Approving a quote must not depend on the health of a rule someone wrote last Tuesday.
2. **Every attempt is visible.** Skipped runs are recorded too, with their reason. A rule that silently does nothing is indistinguishable from a broken one, and "why didn't my automation fire?" is the question this feature will be asked most — which is why run history is a first-class endpoint and an on-page panel rather than a log line.
3. **Running twice does the work once.** Each run computes a dedupe key of `{automation_id}:{trigger}:{subject_id}[:{discriminator}]`, pre-checked and then enforced by a UNIQUE constraint — the same defence-in-depth Sprint 024 established for notification dedupe. Actions carry their own derived keys (`{run_key}#{index}`), so a run that fails at action 2 of 3 and is retried does not double-create action 1's task.

**Conditions are evaluated against an explicitly-built subject dict, never an ORM row.** That is the security property of `app/automations/subjects.py`: if conditions used `getattr(row, field)`, a user-authored rule could name any column, any relationship, or any Python attribute on the model. Because the subject is assembled from a fixed key list, a condition can only ever see what that module deliberately exposed, and an unknown field is a definite `False` rather than an accidental disclosure. Placeholder substitution is a key-walk rather than `str.format()`, for the same reason: `"{x.__class__}"` is an attribute-traversal vector when the template is user-authored.

**Conditions fail closed.** An unknown field or operator makes the whole rule false. Silently ignoring the condition would run the actions of a rule the author believes is narrowly scoped, which is the worse of the two failures by a wide margin.

**Templates are definitions, not rows.** Nothing is written to a workspace until someone activates a template. Auto-creating automations at signup would mean a workspace starts producing tasks and notifications nobody asked for, from rules they have never read — which is how automation features come to be distrusted and switched off wholesale. Activation round-trips the template through the same `AutomationCreate` validation a hand-written rule passes, so a template edited into something invalid fails loudly at activation rather than writing an unrunnable rule.

## ADR-041: GeoCore AI names the engine that answered
**Status:** IMPLEMENTED (Sprint 036, Workstream H)

Two genuinely different things in this codebase have both been called "AI": a real LLM (`app/quotes/ai_draft.py`, available only when `OPENAI_API_KEY` is configured) and `app/brain/BrainManager`, a keyword router over the material catalogue. The `/ai-assistant` page blurred them — it rendered `JSON.stringify` output in a `<pre>` and its own product copy named `POST /process`, `BrainManager` and a sprint number.

**Every response carries `engine`.** `"llm"` means a real model answered; `"builtin"` means the deterministic catalogue assistant did, because no provider is connected or the provider was unreachable. The interface renders that distinction rather than hiding it, and `GET /api/v1/ai/capabilities` lets the UI describe the deployment it is actually running in instead of advertising capabilities that would silently do nothing.

**A provider outage degrades rather than errors.** An unreachable provider falls back to the built-in assistant and labels the reply as such. Returning a 502 for a material-price question the deterministic path could have answered would be worse for the user and no more honest.

**What is sent to the model is bounded, tenant-scoped and free of personal data.** `app/ai/context.py` builds counts, totals and at most five headline titles from the caller's own tenant. No customer email addresses, phone numbers, addresses or message bodies leave the database: they have no bearing on "how many quotes are outstanding", and sending them anyway would be a privacy decision made by accident. A backend test asserts a real customer's contact details do not appear in the prompt.

**The assistant has no tools and cannot write.** It cannot create a quote, change a price, send anything or modify any record, and it says so in the interface. A write-capable assistant needs a permission model, a confirmation step and an audit trail; shipping it without those would be the kind of feature that has to be switched off a week later.

**Conversation state is client-side, and that is a stated boundary rather than an oversight.** There is no conversations table, so a conversation lasts as long as the tab. Persisting it is a real feature — search, sharing, audit — and is recorded as follow-up work rather than half-built.

## ADR-042: A trade-adaptive workflow engine sits alongside the legacy pipeline, never replaces it mid-migration
**Status:** IMPLEMENTED (Sprint 040 — GeoCore Premium OS Plan 01: Adaptive Workflows + Project 360 Foundation)

`ProjectStatus` (ADR-022) is a single, hard-coded 7-value pipeline whose own vocabulary — `templated`, `fabricated`, `installed` — is stone-industry language forced onto every trade GeoCore now serves (ADR-039 made the *quote* side trade-adaptive; the *project* side stayed stone-shaped until this plan). Building a real per-trade pipeline meant answering a harder question than "add more statuses": how do 27 trades each get their own real stage sequence, how does a dashboard still report across all of them in one number, and — the constraint every other decision here serves — how does every project that already exists keep working, unchanged, throughout.

**A new, versioned schema (`workflow_templates`/`workflow_stages`/`workflow_transitions`/`project_workflow_history`) is additive, not a replacement.** `projects.status` is untouched by the migration and stays the live field every pre-existing consumer reads and writes exactly as before — `PipelineCounts`, the pre-Task-8 frontend, any direct API integration. The new `workflow` view is genuinely new information sitting next to it, the same "two equally valid fields during a migration period" shape `ProjectOut` already uses elsewhere in this codebase. Nothing in this plan deletes the status column, and nothing was required to.

**Every existing project is bound to an immutable `legacy_v1` template whose 7 real stage keys are, by construction, exactly the historical `ProjectStatus` values — never guessed, never reinterpreted.** The migration's own backfill matches a project's `status` string to the identically-named stage key; there is no heuristic, no "closest trade" inference, and no case where `templated`/`fabricated`/`installed` gets reinterpreted for a non-stone historical project. A **new** project (including one created via quote handoff) is bound instead to its own trade's real system template, resolved from the quote/project's own `trade`/`project_type` — an unknown or absent trade falls back to a safe general template, never assumed to be stone.

**Stable machine `key`s and a separate semantic `role`, never the display `label`, are what the system reasons over.** A stage's `label` ("Fabrication", "First Fix") is what a person reads; its `role` (one of 13 fixed values: `lead`, `survey`, `quoted`, `approved`, `procurement`, `scheduled`, `in_progress`, `inspection`, `snagging`, `handover`, `completed`, `on_hold`, `cancelled`) is what a dashboard, an automation or the AI context reads. This is what lets `PipelineRoleCounts` (Task 7) show one company-wide "in progress" number across a stone job on "Fabrication" and an electrical job on "First Fix" without forcing one trade's vocabulary onto another, or without the platform ever deriving business logic from a rewordable label.

**Hold and Cancel are real stages with a real `workflow_stage_id`; Resume is a service-layer special case, not a graph edge.** Every template — legacy included — gets two synthetic side stages appended after its real sequence, `on_hold` (non-terminal) and `cancelled` (terminal), with universal edges from every non-terminal real stage into each. This gives Hold/Cancel the same first-class representation as any other move (a real row in `project_workflow_history`, gate-checkable, listed as an ordinary allowed transition) without polluting the ordered forward sequence a template's own tests assert against. Resume's target varies per project — "wherever it was before" — so it is deliberately **not** a static `workflow_transitions` row; `app/workflows/service.py` recognises it by comparing the requested target against the project's own `workflow_previous_active_stage_id`.

**A stage's entry gates are a closed, validated set, never arbitrary code.** `WorkflowStage.gate_definitions` (JSONB) holds a list validated through a Pydantic discriminated union (`app/workflows/gates.py`) into exactly five initial types — `customer_linked`, `assigned_user`, `site_address_present`, `completed_site_visit`, `approved_source_quote` — each evaluated against real, already-tracked project state (a column, or a real related Appointment/Quote row). An unrecognised gate type fails loudly rather than silently admitting an unenforced requirement. Extending this to a later gate (payment, procurement, a document, a certification, a checklist) is one more union variant and one more evaluation branch — the transition engine itself never changes, and gate results ride the same `WorkflowTransitionOption` the frontend already reads, never a second, driftable copy of the reasoning.

**The two endpoints that can move a project's stage keep the legacy binding's two fields in lockstep, symmetrically, without merging their concerns.** `PATCH /projects/{id}/status` (ADR-022's own endpoint) also updates `workflow_stage_id` when the project is `legacy_v1`-bound; the new `POST /projects/{id}/workflow/transition` also writes `status` under the same condition. Neither endpoint touches the other field for a project on a real trade workflow, where no such 1:1 mapping exists — `status` simply stays whatever it was created as, and `workflow` is the only view that ever moves. This is what lets Project 360 (Task 8) drive every project's advancement action through one endpoint, legacy-bound or not, without a parallel UI branch for "old" projects.

**Project 360's tabs are only what has a real, non-fabricated data source today.** Overview, Workflow, Schedule, Team, Tasks and Timeline each read something the backend actually returns; there is no Financials, Materials, Documents, Variations or Photos tab, because nothing backs them yet — a placeholder tab a person can click into and find nothing is worse than no tab. The Workflow tab itself does not attempt to draw a full linear progress bar across "every stage in the template," because no endpoint exposes a template's complete ordered stage list — only a project's current stage and its own legal next moves. Inventing a fuller picture from what little the frontend happens to know would be exactly the kind of fabricated state this plan's own contract forbids.

Sprint 039 Blocker 7 deliberately erased stone from the top-level positioning — `apps/marketing/positioning.test.mjs` asserted the hero and `SITE_DESCRIPTION` matched "construction and renovation businesses" and explicitly forbade the phrase "stone and construction," locking in "trade-neutral, not stone-first" as a permanent contract enforced in CI. The previous version's own header explains why it existed; this one explains why it changed and points here. ## ADR-044: The Master Catalogue is a real supplier hierarchy with no price in it; commercial data is tenant-owned, and a surface's name is never its identity
**Status:** IMPLEMENTED (Sprint 042 — GeoCore Premium OS Plan 03: Master Materials & Supplier Catalogue + Stone Quote Engine V2)

Every stone quote before this plan priced from `app/materials/`'s flat, ~30-row reference table — one row per (material name, thickness), looked up by free-text match, with no notion of who sells it, who makes it, or what a given fabricator actually pays for it. That was adequate for a demo catalogue; it cannot represent a real stone business, where the same visible name ("Calacatta Gold") is sold by several different suppliers under several different manufacturers at genuinely different costs, and where "the price" is never one universal number GeoCore itself could know.

**The catalogue is a real hierarchy — Supplier → Manufacturer → Brand → Collection → Surface → Variant — with each level its own table, never collapsed.** A supplier (who a fabricator buys from) is not a manufacturer (who quarries/produces it), which is not a brand (a manufacturer's own product line); a surface can be sold by several suppliers, and a manufacturer's brand can be sold through several suppliers. Collapsing these into a single "material" row, as the legacy table does, cannot represent any of that — it was the right shape for an illustrative demo catalogue and the wrong shape for supplier/pricing reality.

**A surface's `canonical_name` is explicitly, deliberately not a safe unique identity.** Two different suppliers' rows can and do share a visible name, and nothing about this schema deduplicates or merges them on that basis. `app/catalogue/dedupe.py::score_candidate_match` requires a shared `material_family` as a hard prerequisite (a mismatch scores zero outright, regardless of name), treats a matching SKU under the same supplier/manufacturer as a near-certain duplicate, and caps a same-name-only match (no shared supplier, manufacturer, brand or SKU) well below the duplicate threshold. `tests/test_catalogue.py` asserts the coexistence case directly: the same name under two different suppliers is never flagged as a duplicate.

**The global catalogue carries zero pricing columns — not one.** `catalogue_surfaces`/`catalogue_surface_variants` describe only public, factual reference data (names, hierarchy, thickness, finish, slab size, provenance); every commercial figure — buy cost, markup, margin, selling price, stock, lead time, a preferred supplier's account reference — lives exclusively in `tenant_catalogue_overrides`, scoped to one tenant, never read across tenants, and never inferred or guessed when absent (`resolve_price_per_slab` returns `None`, and `QuoteCalculator` raises `CataloguePriceMissingError` — a 400, never a substituted figure). This is both a legal boundary (a supplier's own list price is not GeoCore's to publish, and a tenant's buy cost is never another tenant's business) and the correct commercial shape: two fabricators using the identically-catalogued Calacatta Gold pay different prices for it, and the schema makes that the only possible outcome rather than an accident to guard against.

**A tenant's own private materials reuse the established global/tenant-private idiom (`tenant_id IS NULL` = global) rather than a second, parallel "custom materials" table.** `WorkflowTemplate` (ADR-042/Plan 01) already established this exact convention for system-vs-tenant-owned rows; `catalogue_surfaces.tenant_id` follows it directly. A custom material a tenant saves ("Can't find your stone? Add custom material" → "Save to my private catalogue") is a perfectly ordinary `CatalogueSurface` row with `tenant_id` set, searchable and reusable exactly like a global one, but invisible to every other tenant by construction (`crud.search_catalogue_surfaces`/`get_catalogue_surface_by_id` both filter on `tenant_id IS NULL OR tenant_id = :caller`) — never a second schema shape to keep in sync with the first.

**Price resolves at the surface level by default, with a variant-specific override only when one actually exists.** A tenant who sets one price for a surface ("we buy this at £X, mark up 30%") almost always means that price to apply to any thickness or finish they later quote, not to one specific variant they happened to be looking at — `TenantCatalogueOverride.surface_variant_id` is nullable for exactly this reason, and no DB-level `UNIQUE(tenant_id, surface_id, surface_variant_id)` constraint exists (Postgres treats `NULL <> NULL` in a unique index, making that constraint unreliable with a nullable column) — uniqueness is instead enforced at the service/CRUD layer via an explicit get-then-update-or-insert (`crud.upsert_tenant_catalogue_override`). `QuoteCalculator._resolve_catalogue_item` looks up the override at the quote item's own variant first, falling back to the surface-level row when no variant-specific one exists, so a surface priced once prices correctly for every one of its variants.

## ADR-045: A quote's catalogue-derived commercial data is snapshotted once, at creation, and never re-read afterwards
**Status:** IMPLEMENTED (Sprint 042 — GeoCore Premium OS Plan 03: Master Materials & Supplier Catalogue + Stone Quote Engine V2)

A quote is a document a customer holds a copy of. If a catalogue-linked line item's price, supplier or material name were computed live from the catalogue every time the quote was viewed, then renaming a surface, correcting a supplier link, or simply updating this month's buy cost would silently rewrite every past customer's quote — the same category of problem ADR-036/ADR-037 already solved for tenant company identity, applied here to commercial pricing instead of branding.

**`QuoteItem.catalogue_snapshot` (JSONB) is written exactly once, at `QuoteCalculator._resolve_catalogue_item`, and is never re-read from `catalogue_surfaces`/`catalogue_surface_variants`/`tenant_catalogue_overrides` after that.** It captures everything a reopened quote needs to display honestly: surface name, supplier, manufacturer, brand, collection, material family, thickness, finish, slab size, the cost and selling price actually used, and which precedence rule produced that price (`margin_basis`: `"selling_price"`/`"markup"`/`"margin"`). `QuoteItem.price_per_slab`/`line_total` — the columns every existing reader (the PDF, the portal, the dashboard) already reads — are the same frozen values, so nothing downstream needed to learn about the new JSONB column to stay correct.

**Proven directly by regression test, not by implication.** `tests/test_catalogue.py::test_catalogue_quote_creates_an_immutable_snapshot_that_survives_later_catalogue_changes` creates a catalogue quote, then renames the surface and changes the tenant's price, then reopens the *original* persisted `QuoteItem` row and asserts its snapshot, `price_per_slab` and `line_total` are all exactly what they were at creation. `e2e/master-catalogue.spec.ts`'s Journey A repeats the same proof through the real browser end to end, including reloading the quote's own detail page after the price change.

**`catalogue_surface_id`/`catalogue_variant_id` on `QuoteItem` remain live foreign keys, deliberately alongside the frozen snapshot, for a different purpose: "where did this line come from," not "what does it cost."** They let a future feature (e.g. "quote this surface again," or a supplier-side sales report) trace a historical quote line back to its catalogue origin without needing to parse the snapshot JSON — but no code path anywhere re-derives price, name or supplier from them once the quote exists. Both are nullable and additive, so every quote item created before this migration, and every free-text (non-catalogue) line created after it, carries `NULL` in all three catalogue columns and behaves exactly as it always has.

## ADR-046: The global catalogue has no admin UI and no auto-publishing scraper — it is written only by a controlled, offline, idempotent script
**Status:** IMPLEMENTED (Sprint 042 — GeoCore Premium OS Plan 03: Master Materials & Supplier Catalogue + Stone Quote Engine V2)

`UserRole` has exactly two values, `OWNER` and `STAFF` (`docs/USER_ROLES.md`) — there is no platform-admin role anywhere in GeoCore, and this plan deliberately does not invent one just to gate a catalogue-management screen. Building an admin role, an admin API surface and an admin UI would be real, ongoing product surface area for a need this plan can meet more safely and far more cheaply.

**Every global (`tenant_id IS NULL`) catalogue row is written by one path: `python -m app.catalogue.seed` (`app/catalogue/seed.py`), run manually against a target database, never by an HTTP endpoint and never wired into application startup.** This is a deliberate departure from `app/materials/seed.py`'s pattern (a `SEED_DATA_ENABLED`-guarded auto-seed that runs on every boot) — the master catalogue's seed data carries real-world supplier/manufacturer/brand claims, and an unattended auto-seed re-running against a long-lived production database is exactly the "uncontrolled scraper publishing directly to production" shape this plan's own contract forbids. A human runs the script, on purpose, when there is real data to add.

**The script is idempotent by construction, not by convention.** `seed_catalogue()` looks up every manufacturer/brand/supplier/surface by its slug before creating one, so re-running it against a database that already has the seeded rows creates nothing new (`tests/test_catalogue_seed.py::test_seed_catalogue_is_idempotent_and_never_seeds_a_price` asserts exactly this: a second run's `surfaces_created`/`variants_created` are both zero, and the surface count is unchanged). It seeds no pricing whatsoever — the schema itself has nowhere to put one — and every seeded surface carries `source_name`/`source_verified_at`, so provenance is recorded from the first row rather than added retroactively.

**Seed data is deliberately representative, not exhaustive, and never copies anything proprietary.** The initial set covers well-known public supplier/manufacturer/brand names (Cosentino, Silestone, Dekton, and similarly-scoped others) using only public, factual reference data — names, material family, thickness, finish, slab dimensions, a public SKU where verified — never a competitor's product photography, marketing copy, page layout, or list pricing. A tenant's own private catalogue (ADR-044) and the custom-material fallback are what actually gets a real fabricator's specific stone into GeoCore quickly; the global seed exists to make search feel populated on day one, not to be a complete supplier database.

**A tenant-authorised search of the catalogue (including by GeoCore AI, `app/catalogue/ai.py::search_for_ai`) is read-only with respect to commercial truth.** The AI may find and describe a surface, but every result carries an explicit `price_available: bool` rather than omitting price when none is set — the same "never fabricate, always say so explicitly" contract `app/materials/search.py`'s found/multiple/not_found result already established for the legacy catalogue. Writing catalogue data (a tenant's own price, or a tenant's own custom material) stays a deliberate, authenticated, human action through the ordinary API — never something the AI does on its own.

## ADR-047: A project's base contract value comes only from its linked, approved quote — never the mutable `estimated_value`, never a guess
**Status:** IMPLEMENTED (Sprint 043 — GeoCore Premium OS Plan 04: Job Financials + Variations)

Every figure in the new commercial-control layer (current contract value, forecast profit, forecast margin) is built on top of one number: what was actually agreed with the customer before any variation. GeoCore already has a column that looks like this — `Project.estimated_value` — but its own docstring says plainly that it "legitimately moves as variations are agreed," which makes it exactly the wrong source: a base figure that can drift is not a base figure at all, and computing "current contract" from a value that variations already adjust would double-count every variation the moment it was approved.

**`resolve_base_contract` (`app/financials/service.py`) uses exactly one source: `Project.quote_id`, when set.** This is safe by construction, not by convention — `QuoteService.handoff()` is the only code path that ever sets `Project.quote_id`, and it refuses to hand off any quote whose status is not `"approved"` (`app/quotes/service.py`). A linked quote is therefore *always* an already-approved commercial document, and `Quote.total` is the one number in the whole schema that represents "what this customer agreed to pay" and is never silently rewritten afterwards (see ADR-045's snapshot guarantee, which makes it durable too). A project with no linked quote (a bare enquiry, or one created outside the quote-handoff flow) gets `base_contract_value = None` and `base_contract_source = None` — never a guessed zero, never `estimated_value` as a fallback.

**This is deliberately conservative and will under-report before it ever over-reports.** A project whose commercial history predates GeoCore, or whose quote was approved through some future alternate path, shows "Unknown — no approved quote linked" rather than fabricating a number from whatever happens to be in `estimated_value`. Widening the source list (an explicit "approved contract value" field a person can set directly, for exactly this case) is real future work, not something this ADR tries to solve by relaxing the rule.

## ADR-048: Current contract value is always derived by summing approved variations, never maintained by incrementing a running total
**Status:** IMPLEMENTED (Sprint 043 — GeoCore Premium OS Plan 04: Job Financials + Variations)

The sprint's own contract names the single regression that matters most here by name: approving the same variation twice must never increase the contract twice. A naive implementation — `project.current_contract_value += variation.total` on approval — cannot make that guarantee under retry, duplicate click, or double webhook delivery; it has no memory of which variations it has already counted, only a running total that keeps moving.

**`current_contract_value` is not a stored column anywhere. It is computed fresh on every read** as `base_contract_value + SUM(total) over this project's variations WHERE status = 'approved'` (`build_contract_summary`, fed by `crud.sum_approved_variations_total`). A variation's own `status` is the only state that matters; a transition to `"approved"` either happens once (changing `status` from `draft`/`sent` to `approved`) or is a no-op (the variation is already `approved`). `VariationService._transition` enforces the no-op explicitly: if `variation.status == target`, it returns immediately without touching `approved_at`, without writing a second `ActivityLog` entry, and without dispatching a second automation — a retried approval request is indistinguishable, in every observable effect, from doing nothing.

**Proven directly by regression test**, not by code inspection alone: `tests/test_job_financials.py::test_approving_a_variation_twice_increases_the_contract_exactly_once` approves the same variation three times — twice through the service layer directly, once more through the live HTTP route — and asserts `approved_at` is unchanged and `approved_variations_total` stays at its single-approval value throughout. `e2e/job-financials-variations.spec.ts` repeats the same proof through the real browser and a direct API retry, reading the figure back from the real Project 360 Financials tab after a page reload.

**The corollary this pattern rules out by construction: a variation can never be "unapproved" by editing it back to draft.** `ALLOWED_TRANSITIONS["approved"]` is the empty set — approved, rejected and void are all terminal. A wrong variation is corrected by voiding it and raising a new one, never by rewriting history (the same "correction, not rewrite" pattern quotes already use once approved).

## ADR-049: Forecast cost is a simple sum across cost states, deliberately not a reconciled one — and every profitability figure is gated on real cost data existing
**Status:** IMPLEMENTED (Sprint 043 — GeoCore Premium OS Plan 04: Job Financials + Variations)

A more sophisticated forecast-cost formula is easy to imagine — "count a committed cost only for the portion not yet actualised," or "replace a budgeted line once its committed counterpart appears" — but building it correctly requires a cost model with an explicit lineage between rows (this budgeted line became that committed line, which became this actual line), and GeoCore's `project_cost_entries` table deliberately has none: a cost item is *one row*, edited in place as it graduates budgeted → committed → actual (`app/database/models.py`'s own docstring on `ProjectCostEntry`). Building a reconciliation engine on top of a schema that has no lineage to reconcile would be exactly the "fake sophistication" the sprint's own contract warns against.

**`forecast_cost = budgeted_cost + committed_cost + actual_cost`, a plain sum with no clever inference.** This is safe from double-counting for the reason above, not despite it: because a real cost item's state changes are recorded by editing its one row, never by inserting a second row for the same underlying cost, the sum never contains two rows describing the same piece of work at different stages. The cost this simplicity: a fabricator who deliberately keeps a *separate* budgeted line and a *separate* committed line for genuinely different scopes gets the correct, additive answer; one who edits a row's state as intended also gets the correct answer; the only failure mode is a fabricator manually duplicating a cost across two rows instead of editing one in place, which is a data-entry error the UI does not currently prevent and is documented here as a known limitation, not silently "handled" by guessed heuristics.

**No profitability figure is ever computed from partial confidence dressed up as certainty.** `build_profitability_summary` requires both a known `current_contract_value` (which itself requires a known base contract) *and* at least one recorded cost entry before computing anything — a project with a contract but zero costs shows "Unknown," not a forecast profit equal to the full contract value (which would imply zero cost, a claim GeoCore has no basis to make). `cost_data_status` (`none`/`partial`/`complete`) is surfaced alongside every forecast figure specifically so a "confident-looking" £4,000 forecast profit is never presented without the caveat that it may still move — `complete` is reserved for a project whose own workflow has reached its `completed` role, the one honest signal that no more cost entries are coming.

**The margin-risk threshold (15%) is a documented, conservative internal default, not a tenant-configurable business policy this sprint invents.** No existing settings surface lets a tenant define their own acceptable margin, and building one was explicitly out of scope; `MARGIN_RISK_THRESHOLD_PERCENT = 15.0` (`app/financials/service.py`) is deliberately conservative (many trades in this industry run tighter than that) so the flag under-warns rather than over-warns, and `margin_risk` is only ever `True` when `forecast_gross_margin_percent` is both known (real cost data exists) and below the threshold — never inferred from partial or missing data. Tenant-configurable thresholds are named here as the natural next step, not attempted in this migration.

## ADR-050: A purchase order's reference number is sequential per tenant, not per project — because a PO's project is optional
**Status:** IMPLEMENTED (Sprint 044 — GeoCore Premium OS Plan 05: Procurement + Materials Operations)

Every other document-numbering scheme GeoCore already has — a variation's `V-001`, a quote's own id — is scoped to something the document always belongs to: a variation always has a project, a quote always has a customer. A purchase order does not have that guarantee: `purchase_orders.project_id` is nullable by design (Task 3), because a fabricator legitimately raises POs for workshop stock or general consumables with no single project to attribute them to. A per-project sequence (`V-001` restarting at 1 for every project) has nowhere to live when `project_id` is `NULL`.

**`PurchaseOrder.reference` is therefore sequential per tenant** (`ProcurementService._next_po_reference`, backed by `crud.count_purchase_orders_for_tenant`), giving every tenant one continuous `PO-001`, `PO-002`, … sequence regardless of which project, or no project, each one is raised against. The cost of this choice is one a fabricator would recognise immediately: a tenant with many projects will see PO numbers "skip" within any single project's own view, exactly as their own paper purchase-order book already does. The alternative — inventing a synthetic per-tenant counter for variations too, or forcing every stock PO to be attached to a placeholder project — was rejected as solving a numbering aesthetic by breaking a real modelling distinction (Task 14's own "not a warehouse system" boundary depends on a PO being allowed to exist independent of a project).

## ADR-051: A purchase order's committed cost is created at approval, and a partial receipt deliberately does not split it — the documented V1 simplification
**Status:** IMPLEMENTED (Sprint 044 — GeoCore Premium OS Plan 05: Procurement + Materials Operations)

Task 8 ties a PO's pricing lock to its approval step, so the natural point to record its commercial impact on the project is the same moment: `ProcurementService.approve()` creates exactly one `ProjectCostEntry` per PO item, `state="committed"`, guarded by an existence check on `purchase_order_item_id` so retrying approval — through the service layer directly or through a repeated HTTP request — never creates a second row for the same item (the identical idempotency shape `tests/test_job_financials.py` already proved for variation approval, reused here rather than reinvented).

**A harder question is what happens to that committed row when only part of an item's quantity has been delivered.** The sophisticated answer — split the committed amount proportionally between "still committed" and "now actual" as receipts land — requires a cost model with explicit lineage between rows (this committed amount became that actual amount), and `project_cost_entries` deliberately has none: ADR-049 already established that a cost item is one row, edited in place as it moves through its lifecycle, precisely so `forecast_cost` stays safe from double-counting without a reconciliation engine. Building partial-receipt splitting on top of that schema would require either violating the one-row invariant (creating a second row for "the actual portion") or inventing a quantity-weighted state that the schema has no column for.

**The V1 rule GeoCore actually implements: a PO item's committed cost stays `committed`, in full, until that item is completely received — at which point `_mark_item_cost_actual` flips the same row's `state` to `actual` in place.** A partial receipt changes the *requirement's* status (to `partially_received`, visible on the Project 360 Materials tab and the Command Center) but leaves the linked cost entry's figure exactly as it was. This means a project's forecast cost briefly overstates "how actual" a partially-delivered item's cost really is — documented here as a known limitation, not silently hidden — in exchange for a guarantee that is never violated: the sum of every committed + actual cost entry for a PO never exceeds, and never falls short of, that PO's own approved total, under any sequence of partial deliveries (`tests/test_procurement.py::test_a_partial_receipt_leaves_the_full_committed_amount_in_place` and `test_full_receipt_flips_committed_cost_to_actual_in_place_not_a_second_row` prove both halves directly). Reconciling proportional splitting is real future work, gated on giving `project_cost_entries` the lineage it does not have today — not something this migration tries to approximate.

## ADR-052: The "materials ready" workflow gate and Command Center signal check a real, current gate evaluation — never "has an outstanding requirement somewhere"
**Status:** IMPLEMENTED (Sprint 044 — GeoCore Premium OS Plan 05: Procurement + Materials Operations)

The cheap way to build a "blocked by materials" signal is a query: count projects with at least one `project_material_requirements` row whose status is not yet terminal. That query is honest about requirements but dishonest about *blocking* — a requirement can be outstanding on a project that is nowhere near its materials-gated stage yet (an enquiry-stage stone job with a planned worktop requirement is not "blocked," it simply hasn't reached Fabrication), and a naive count would flag it anyway.

**Both the workflow gate and the Command Center signal instead call the one real evaluator, `evaluate_stage_gates`** (`app/workflows/gates.py`), against the project's actual current stage. `MaterialsReadyGate` contributes a blocker only when the project's requirements include at least one in `REQUIREMENT_BLOCKING_STATUSES = {planned, required, ordered, partially_received}` *and* the project's current stage actually carries that gate — the same function the transition engine itself uses to decide whether a move is legal, so the dashboard signal and the enforcement mechanism can never disagree about what "blocked" means. `_build_procurement_signals` (`app/dashboard/service.py`) runs this per-project rather than as a single aggregate query, the same documented, bounded-loop exception to the Command Center's own "O(1) queries" convention that Plan 04's margin-risk signal already established (ADR-049's sibling decision, same file) — correctness over query-count purity for a signal a fabricator will act on directly.

**A project with zero material requirements is never blocked**, regardless of its stage — proven directly by `tests/test_workflows.py::test_materials_ready_gate_blocks_then_clears_as_requirements_are_received`, which asserts the unblocked case first before ever creating a requirement, specifically so this ADR's claim is checked by a real assertion rather than left as a design intention.

## ADR-053: Catalogue free text searches what a surface *is*; a supplier matches only what it actually sources for the searching tenant

**Context.** Production catalogue search returned nothing because the global reference data was never loaded, and the search box itself had three weaknesses. A single `ILIKE '%query%'` over the whole string meant "white quartz" matched nothing (no product is named that). Material family and colour were exact filters that the quote page's search box never used. And text matched any supplier's name, although seeded suppliers source no surface, so a supplier match was either empty or meaningless.

**Decision.**
- Free text is split into words (`app/catalogue/search_terms.py`, at most 6). **Every word must match**, and each word may match the surface's name, brand or manufacturer by substring, or its material family or colour **by meaning**. Family and colour words go through a small closed vocabulary ("sintered" → `sintered_stone`, "gray" → `grey`, "cream" → `beige`) rather than a substring of a product name.
- A **supplier is where a surface is bought from, not what it is.** A supplier (by name in free text, or by `supplier_id` filter) matches a surface only when it is that surface's own catalogue supplier, or this tenant's `preferred_supplier_id` on its own `TenantCatalogueOverride`. One tenant's supplier choice never changes another tenant's results. Implemented as EXISTS clauses, so variant-level overrides never duplicate a result.
- `GET /api/v1/catalogue/meta/status` reports how many global and tenant-private surfaces the caller can see, so the UI says "the catalogue is empty" separately from "nothing matched".
- Reference data gets a read-only release gate (`python -m app.catalogue.reference_data`, exit 0/1) derived from the seed's own definitions and slug rule, and the seed gains `--dry-run` and a mandatory `--confirm-production` (PRODUCTION_RUNBOOK §13).
- **The seed contains no suppliers.** The two placeholder distributors seeded since Sprint 042 were referenced by no surface, variant or override, yet would have appeared in every workspace's supplier lists. They are removed from the seed, the gate fails if either placeholder slug exists, and supplier search relies solely on real suppliers a tenant configures (its own materials and preferred suppliers).

**Consequences.** Multi-word searches narrow instead of widening. A free-text word that is neither in a name nor a known family/colour word finds nothing, which is the honest result. The gate is deliberately not part of `/ready`: production is currently missing the data, and failing readiness would take the whole API down for a catalogue-only defect.
